013: Practices from sibling repositories
======================================
Date: 2026-10-16
Status: synthesis and implementation guidance; findings are not all implemented

Purpose and evidence
--------------------
Carry forward useful practices and the reasons behind them from Magnet,
NMRPeak and SECS. The study covered current implementations, regression tests
and selected corrective history. Independent read-only reviewers examined each
sibling. Reading a regression establishes its intended assertion; these reviews
did not rerun the sibling suites or establish current deployed behavior.

Use means applicable guidance, with adoption status stated below. Avoid names
failure patterns or inappropriate adaptations. Not applicable means outside the
current contained baseline and planned label-free coordinate slice; reconsider
only when a real consumer appears. This note does not authorize upstream edits,
new acquisition, provider integration or a broad foundation refactor.

Use
===

U01. Preserve one scientific implementation beneath thin checkpoint variants.
NMRPeak's HF adapter supplies tokenizer choices and materialization to the shared
family runtime. SECS calls encode_modality beneath training forward composition.
For 002, share tensor preparation and invocation between H/C while keeping each
checkpoint/scaler pair explicit. Use the real UniMat head without training task,
labels or loss. Planned already; no service framework is needed.
Refs: P:models/nmrpeak_hf_v1/runner/runtime.py:20;
S:secs/src/secs/models/model.py:46; N:notes/002_label_free_coordinate_prediction_20261014.txt:29.

U02. Expose scientific transformations as inspectable ordered steps.
SECS resampling averages a piecewise-linear signal over bins, then normalizes;
the loaded boundary additionally max-normalizes and reverses the axis. Ordinary
point interpolation is a different algorithm. Preserve 002's actual float32
cast, centering, distance, special-token and padding order. Planned already.
Refs: S:src/secs_inference/spectra/secs.py:16,38;
S:src/secs_inference/model.py:141.

U03. Carry identity from the same selection that controls computation.
G01 uses one ordered CPU nucleus layout for gathering features and returning
atom indices. For 002, derive the upstream mask and original-index crosswalk
from one ordered atom traversal. Keep supplied atom order; no reparsing or
canonicalization should reconstruct identity after prediction. Planned already.
Ref: M:models/g_01_nmr_forward/magnet/stairway/g_01_nmr_forward/dataloader/collator.py:58.

U04. Check semantic compatibility as well as tensor compatibility.
E02 compares configured normalization buffers before strict loading overwrites
them. Matching keys and shapes alone do not prove the intended normalization.
Keep dictionary ordering, paired scaler identity, full state compatibility and
actual device/dtype checks separate. Existing baseline checks and 002 cover this.
Ref: M:models/e_02_ch_nmrexp/magnet/stairway/e_02_ch_nmrexp/inference.py:104,307.

U05. Bind verification to the bytes consumed.
NMRPeak keeps a verified, rewound checkpoint descriptor through loading; its test
replaces the pathname and still reads admitted bytes. Our verified_member hashes
and returns a path. Strengthen 002's checkpoint/scaler/dictionary contract, using
existing artifact ownership. A held descriptor prevents pathname substitution,
not in-place writes to that inode; an immutable verified buffer or enforced
nonmutation through consumption is needed for that stronger guarantee.
Refs: P:families/nmrpeak/checkpoint_file.py:34;
P:tests/unit/test_checkpoint_file.py:23; N:tools/baseline_prepare.py:157.

bundle supporting published claims beyond ignored working directories. Bind
derived oracle fixtures to exact producer bytes as well as source records, and
assert the exact historical fixture-key and 64-position sets before iterating.
These are narrow qualification refinements, not a new evidence registry.

already happened. Priority alignment (2026-10-17): 002 defers the standalone
prediction CLI and its product result-publication protocol. This rule preserves
safe qualification evidence and provider reporting; it does not require creating
another publication owner. See 002's dated priority correction and completion

Maintainer directions adopted after log review
---------------------------------------------
The maintainer explicitly selected these recurring directions for this
note on 2026-10-16. They govern how to apply the practices above. Private log
paths and session details remain outside public history; references below are
public repository examples, not substitutes for the maintainer's instructions.

U15. Preserve requirements by meaning and intent.
Do not weaken a check to obtain a passing result. Establish the requirement it
protects, retain that obligation, and remove brittle wording assertions,
implementation-shaped tests or ceremonial proof requirements when they add no
protection. A failing applicable check is a finding to resolve, not an automatic
reason to narrow its scope. Adapt precedent only as much as local ownership and
long-term maintainability require.
Example: explanation-only annotations retain the detector and placement rules
without requiring a mechanically resolved test reference.
Ref: N:repository_checks/quality/PORTS.md:29.

U16. Record precise sources AND the rationale where they support the work.
Every borrowed behavior, scientific assumption and consequential decision needs
an identifiable source and an explanation of why it applies here. Put that
information beside the relevant code, declaration, result or design decision.
Identify the repository and exact revision/path/section, or the paper version,
release/member identity or retained run that supports the claim. Explain what
the source establishes, what was adapted, and what remains unknown or unverified.
Record why the evidence was consulted and why the chosen behavior follows from
it; a link alone does not preserve the reasoning. For authored notes and results,
state who produced them and their purpose. Keep historical evidence bound to its
actual producer and execution; later observations must be dated separately.
Precise references must remain usable without reconstructing a chat, locating
an unspecified sibling HEAD or guessing which experiment was meant. Keep private
operational evidence separately and publish only appropriate attributable facts.
Examples: this note's pinned source aliases and per-finding rationale;
N:artifacts/SOURCES.md:3; P:docs/benchmark.md:71.

U17. Explain purpose and actionable behavior in plain language.
Lead with what the reader can do, what happened and the next useful action.
Use concrete examples when they clarify a claimed benefit. Explain unfamiliar
terms and important limits; include implementation detail where it helps the
reader decide. Keep failure reasons useful and specific while excluding sensitive
material and unnecessary payload dumps. Privacy must preserve useful diagnosis.
Refs: M:notes/030_implementer_tendencies_20261013.txt:46;
P:notes/006_maximum_error_transparency_20261014.txt:1.

U18. Deliver coherent progress and make its status visible.
Commit meaningful, reviewed slices with explicit paths: git add -- FILE... and
git commit -m MESSAGE -- FILE.... Preserve unrelated changes. Give useful progress
updates, remaining work and evidence-based ETA or uncertainty before repeated
status questions become necessary. Distinguish implemented, tested, qualified and
deployed outcomes. Commit, push, deployment and notification authority remain
task-specific; this guidance does not grant new external actions.
Example of bounded delivery reporting:
N:notes/002_label_free_coordinate_prediction_20261014.txt:1 distinguishes implemented
admission/tensor/orchestration work from pending release-model qualification.

U19. Preserve reproducibility and development rationale with a clear purpose.
Before tidying, identify what each artifact supports, who still needs it and how
long it remains useful. Extract durable findings, decisions, rejected alternatives
that explain the design, and lessons from logs into concise maintained notes,
with precise references and limits. Preserve the underlying observations needed
to reproduce or assess a scientific claim; a prose summary cannot replace them.
Keep reusable offline inputs at their maintained paths. Keep unreviewed runs,
debug captures and temporary helpers under ignored working storage, grouped by
purpose. For published claims, select and publish reviewed, privacy-safe evidence
with inputs, producer/runtime identities, methods and necessary raw observations.
Keep that evidence immutable and distinguish it from the current rerun commands.
Use the existing retention policy: inputs while offline use is needed, evidence
while its claims are published, and debug captures until resolution or acceptance
of reviewed replacement evidence. Remove superseded scratch only after checking
that no unique evidence, useful rationale or active workflow depends on it.
Retained working storage needs deliberate cleanup too; being ignored does not
make an unstructured accumulation useful. This guidance does not authorize a
cleanup now or require committing every run, transcript, download or helper.
Refs: N:README.md:183; N:notes/012_repository_check_log_findings_20261014.txt:4;
P:docs/benchmark.md:57,78.

Further practices selected from sibling AGENTS.md files
------------------------------------------------------

U20. Distinguish deterministic generated artifacts from dependency locks.
For an actual checked-in generated artifact, provide explicit write and no-write
check lanes that render from the same canonical inputs and compare exact output.
Update it through its owner; do not hand-edit generated bytes or recorded hashes.
A lock captures a reviewed mutable-index snapshot. Its offline checks establish
inventory, format and consumer compatibility, not index freshness. Refresh through
an explicit acquisition lane and review the complete package-set diff. Do not add
empty generator machinery when no corresponding artifact needs it.
Refs: I:AGENTS.md:89,176; V:AGENTS.md:39.

U21. Require explicit review when a reference implementation version changes.
Version-sensitive expected results must identify the exact reference version.
If a new version has no qualified fixture set, fail with that fact rather than
silently regenerating or redefining expectations. Preserve the earlier reference
and qualify the replacement deliberately. Apply this when such a reference is
used; sampled agreement cannot establish an exhaustive equality claim.
Ref: Q:AGENTS.md:135. This refines U06; it does not add a new dependency to 002.

U22. Keep active guidance current and historical records historical.
When implementation establishes a different fact, update the active design,
instructions, tests and maintained specifications together. Preserve dated
observations and explain supersession; do not rewrite an old record to imply
that today's behavior was observed then. State unresolved product or scientific
questions explicitly instead of filling them with defaults or placeholders.
Refs: I:AGENTS.md:60; M:AGENTS.md:44. This complements U16/U19.

U23. Carry safe causes to the recipient through the channel they use.
Keep failure classification, causal evidence and retry/final disposition distinct:
a status or code alone is insufficient when a safe specific cause is known. Add
owned context across catches and publication without replacing the established
cause with a generic message. Then trace each actual recipient and renderer. A
developer may need a phase and source location; an operator/deployer needs the
attempt or service effect and a safe recovery action; an analysis commissioner
needs to know whether the request was rejected, delayed or failed and what they
can change; a receiver needs to know whether a result exists and what its stated
limits are. These roles may use different channels and need different detail;
terminal stderr is only one possible sink. Keep authorized operational evidence
available even when a public/API surface carries only a condition or bounded
explanation. Magnet keeps operational unavailability separate from caller
rejection and applies retry policy within the Attempt; NMRPeak retains route detail
for its operator while sending a progress condition to the API; SECS publishes a
bounded Attempt explanation and retains structured cause evidence; the GUI
presents an Attempt's failure code and message in the job workspace. These
boundaries matter because they determine who must act next, and raw exception text
may contain protected scientific input. A retry policy is a disposition, not
proof that the underlying cause is transient. At each disclosure boundary, apply
the recipient's authorization and privacy rules: remove secrets and scientific or
host facts that recipient may not receive, while retaining adjacent safe diagnosis.
Check the actual recipient-visible rendering for causal detail, effect state, next
action and redaction; a sanitized outer message can still expose private input
through a cause or traceback. For consequential ambiguous wording, use independent
source review and a context-isolated reader's explanation.

U24. Keep intentionally accepted risks visible and executable.
For a concrete limitation deliberately left unfixed, retain a focused test of
current behavior and explain its consequence and accepted scope. Keep it active;
do not hide stale tests in quarantine or turn a known defect into a desired
permanent contract. Revisit the record and test when the behavior changes.

U25. Separate routine correctness from costly diagnostics and performance.
Keep useful bounded correctness checks in normal discovery. Put expensive
exhaustive witnesses and timing assertions in explicit named lanes, while still
running them when the claim being qualified needs them. A small default check
does not replace exhaustive evidence for an exhaustive claim.
Ref: Q:AGENTS.md:129. Reuse existing contained lanes; no new runner is proposed.

U26. Structure tests by both scope and behavioral purpose.
Added 2026-10-18 following the maintainer's explicit layout direction.
Use the established unit/normative and unit/adversarial split, alongside contract,
integration and scenarios suites where applicable. Normative tests specify required
behavior, including refusal, ordering and atomicity; they are not just happy paths.
Adversarial tests challenge boundaries with malformed inputs, tampering, resource
exhaustion and interrupted effects. Contract tests check external compatibility;
integration tests exercise actual connections between owners. Scenarios tell
recognizable multi-step consumer stories, such as a lost publication reply followed
by restart and exact reconciliation without repeating analysis.

These are complementary distinctions, not a mandatory Cartesian directory tree.
Place each test by its primary purpose; do not duplicate assertions across suites
or create empty scaffolding. Add normative/adversarial subgroups within other
suites when useful. Keep fixture provenance beside its owning suite and share only
needed fakes/helpers. Keep repository checks, model-behavior and live/system/e2e
qualification visibly separate; a worker scenario does not prove an API/GUI flow.
Expose focused hierarchical contained targets for the meaningful suites.

U27. Recover from routine disruption without operator intervention.
Added 2026-10-22 following the maintainer's explicit requirement for resilience
and minimal baby-sitting. A persistent provider should resume useful work after
temporary dependency outages without manual restart, record repair or repeated
configuration changes. Retry only operations whose semantics permit it, at their
existing owner, using configurable capped backoff and request deadlines. Include
jitter where independent clients could synchronize. Waiting remains responsive to
shutdown; account for retries in the applicable work and resource budgets. A
bounded Job budget can end an Attempt without ending the provider service.

Classify failure from evidence: an unknown response or HTTP status alone does not
prove transience. Preserve uncertain mutations and use contract-authorized exact
replay or reconciliation; never repeat scientific work because publication failed.
Resume only after required ownership, identity and retirement facts are established.
Invalid credentials/configuration, permanent rejection and unresolved effects need
distinct dispositions, safe diagnosis and escalation when automatic recovery is
not justified. Report delay, recovery and any required operator action through the
supported recipient channels; retrying must not erase the underlying cause.

Normal successful throughput must not require repeatedly raising history limits
or replacing installation roots. State the intended unattended operating envelope
and give finite history, disk and allocation resources an owned retention,
rotation or renewal policy that preserves unresolved obligations and required
evidence. Hard limits still stop unsafe admission; merely increasing a limit or
documenting the stop does not establish unattended operation.

Assess a recognizable outage-and-recovery sequence and sustained ordinary use:
work resumes without duplicate scientific effects or manual repair, shutdown stays
bounded, and irrecoverable cases explain who must act. Reuse focused existing
scenarios; no mandatory new harness, exhaustive fault matrix or live-model rerun.
