Docker-backed process logging
=============================

Decision
--------
The user's 2026-10-23 instruction supersedes the earlier private-stderr split:
"All should go to bounded docker logs. Remove the file dump path and the dumped
files." Both stdout and stderr now go directly to Docker journald, including
raw tracebacks and completed scientific outcomes attached to exceptions. The
user accepted that these logs can contain molecular data. Existing credential
redaction and RDKit's scoped diagnostic capture remain unchanged.

Use standard Python logging, owned INFO by default, explicit LOG_LEVEL=DEBUG or
WARNING, and a dependency WARNING floor enforced at the root handler even when
a dependency enables its own INFO/DEBUG logger. Imports remain passive. Do not
add twig2, stream replacement, a collector, a queue or a parallel file fallback.

Ownership
---------
tools/provider_logging.sh supplies the shared journald policy: nonblocking
delivery, a 1m buffer, and nmrnet-{{.FullID}} tag. Normal workers, controller,
proxies and finite helper roles all use it. Production launch owners admit the
observed LogConfig alongside their existing isolation/resource posture.
Journald support is required; there is no alternate-driver fallback.

The 1m limit bounds pending delivery, not retained disk. Host journald owns shared
disk/age limits and access. No host configuration is changed. The inspected
existing auto-cleanup-limits.conf declares SystemMaxUse=300M, SystemKeepFree=1G
and MaxRetentionSec=14day. This is not guaranteed 14-day or per-Job retention.
Messages can be dropped or expire. Missing logs establish no lifecycle outcome.

Ordinary process failure reports have one redacted stderr sink. There is no
failure.json or ordinary per-process shutdown-summary file. A failed write keeps
original operation, cleanup and output causes in ProviderProcessFailed; the
existing held-owner finally still prevents release of unresolved work. Clean
shutdown can report unconfirmed Hello/notice-delivery observations without
falsely declaring operation failure. Output failures do not trigger another API
or scientific effect, a file fallback or automatic message resend.

Actual data/control artifacts remain with their owners:
  - admitted startup marker;
  - stopped recovery's functional inspect/replay result.json;
  - scientific outputs and resource snapshots;
  - exact CID, engine-operation, retirement, consumption and replay receipts.
The shared fresh-directory admission still refuses prior result.json because
stopped recovery uses that same directory contract.

Startup helpers previously used stdout for 17/7 NUL-delimited control fields.
They now require --handoff and atomically publish those exact bytes as the
exclusive mode-0600 host-fields artifact using the existing _publish owner.
Successful wait and exact removal still precede adoption. Field counts, bounds,
private ownership and byte-equal recovery admission are unchanged. No binary
protocol is emitted into logs and no new parser or artifact framework is added.

Operator and qualification paths
--------------------------------
  make provider/logs CONTAINER_ID=<full 64-character ID from worker.cid>
reads the latest 200 journal messages, including a removed container's entries.
This is an operator read filter, not a second receipt-admission authority.

  make test/integration/provider/logging
uses the installed image, captured sources and actual service launch/removal
owners for synthetic normal, fatal and host-stop cases. It checks both streams,
fatal traceback/outcome notes and explicit DEBUG after removal. It queries logs
in memory with finite deadlines; it does not create journal exports or stdout/
stderr dump files. Control receipts remain. No credentials, network, API Jobs,
models or scientific accuracy reruns are needed for the logging proof.

All worker/service/prediction-recovery qualification wrappers also inherit both
streams under the same logging policy. Their outer host launchers no longer
write foreground/inspect/recovery/restart log dumps.
