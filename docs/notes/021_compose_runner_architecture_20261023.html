Shared result delivery — design, 24 October 2026

Design only; not implemented. Run one delivery service per Docker host, shared by its providers and runners. It owns durable acceptance and API publication of final immutable completion or failure requests. Providers own scientific decisions, execution and cleanup. This replaces provider result-file dumps and completed-payload history; it does not change molecular inputs, prediction, result formatting or the API contract. Earlier implementation and retention descriptions below record the preceding design.

Small deployment and explicit ownership

Use the existing provider-core package for a small delivery daemon and client. The daemon has no model, RDKit, GPU or Docker-engine access. It is the sole writer of one SQLite database in a named Docker volume. Copy Magnet's private transactional outbox boundary, including durable commits, but omit its retained confirmed payloads. Reuse core's API signing, request/receipt parsing, effect classification and permitted retry behavior; replace the publisher's current dependency on a producer's full Attempt record.

Use SQLite journal_mode=DELETE, synchronous=EXTRA and secure_delete=ON. EXTRA supplies the directory sync for rollback-journal commit durability; secure deletion clears removed content in ordinary database tables. These are built-in settings, not a per-Job vacuum or erasure subsystem. Sources: SQLite commit synchronization and deleted-content clearing.

Give each configured producer its own Unix socket directory, mounted only into that producer and the service. That mount is the handoff capability. Trusted deployment configuration binds the socket to an API origin, expected topology, provider identity, credential and admitted outbound route. Derive those bindings from the existing provider configuration instead of asking operators to maintain a second copy. Producers cannot choose another destination or signing identity, and do not mount the delivery database. Reconfiguration must not retarget queued bodies to another API/provider; a different identity gets a separate binding. Credential rotation may keep the same API/provider identity. Native prediction children continue returning results to their provider.

Handoff and ordinary delivery

  1. The provider finishes its existing result-acceptance decision and encodes the final API request once. It submits those exact bytes to its socket. Delivery does not wait for native cleanup; cleanup still gates safe reuse.
  2. The service admits the complete/fail request using existing core parsers, enforces its byte/item limits and commits the immutable body before acknowledging acceptance. The key is API origin, provider and Attempt; complete and fail are competing choices for that same key.
  3. A repeated outstanding submission with the same operation/body is acknowledged without creating another item. A conflicting outstanding submission is refused without replacing the original.
  4. After the durable acknowledgement, the provider drops its body and the service alone owns publication. It signs each API exchange afresh while preserving the submitted body. Existing API rules decide when exact replay or reconciliation is permitted; a timeout alone grants neither.
  5. After validating the matching API receipt, delete the queue row and body in one transaction. Keep no completed-result archive, permanent tombstone or second producer acknowledgement protocol. Subsequent duplicate submissions can be queued again: the API remains the final authority for already-completed replay and conflict.

The client operations are submit, status for a selected Attempt, and a scoped pending inventory with its capacity summary. Submission carries the operation, Job and Attempt references and exact request bytes; routing comes from the socket binding. Status/inventory return identity, disposition, body digest and safe delay/failure facts, never molecular payloads. The Job reference supplies the existing API read/reconciliation binding. There is no arbitrary HTTP forwarding or model-specific plugin interface.

Retention, capacity and failures

The database holds only outstanding request bodies, their binding/Attempt and Job identity, and retry or held-disposition facts. It does not copy raw Job text, Uploads, preparation arrays, unrounded scientific evidence or transcripts. Bodies may themselves contain the coordinates and shifts selected for the public result. Normal confirmation removes them; an unresolved permanent refusal retains its body for an explicit operator disposition.

Allocate the host's byte/item budget among providers and bound send concurrency. Check capacity before additional computation; an unaccepted result stops further admission and remains bounded by producer concurrency. Enqueue is the authoritative capacity check, not a promise made by an earlier status read. Queue-full or unavailable storage returns no acceptance acknowledgement. There is no direct-send fallback or silent result eviction. Pace permitted retries with capped jittered backoff and request deadlines. A held item must not block other items; one provider's outage must not occupy all delivery slots or consume another provider's capacity.

Decision, purpose and completion contract

The product remains a provider of atom-indexed H/C chemical shifts from admitted molecular geometries. Operating it should require a named deployment, its private inputs and a Docker engine, rather than maintaining an application-specific host daemon. Copy the established Compose/container/session-supervisor boundaries; adapt them to NMRNet's existing scientific and durable execution owners.

Target platform: Linux with Docker Engine and Compose v2. Explicit host-interface binding, Unix sockets and the donor supervisor's Linux process facilities are requirements. This is portability between supported Linux installations, not a claim of Windows, macOS, rootless-engine, ARM or arbitrary orchestrator qualification. Preserve the currently qualified image architecture; declare and verify any further platform separately.

  1. A finite deployment command starts the admitted stack, verifies startup and returns. Containers continue after the invoking shell exits and recover after engine/host restart according to their declared policy.
  2. No production component depends on a permanent host Bash monitor, a custom systemd unit, a Docker socket grant or per-Job Docker commands.
  3. One serial provider session owns each runner session. Native child exit and request completion have different evidence. Neither socket EOF nor a healthcheck proves child retirement or successful science.
  4. The existing controller/store remain the sole owners of admission, durable execution entry, retained outcomes and permitted API replay. A container restart creates no new authority to repeat interpretation or computation.
  5. Scientific inputs, atom order, units, conformers, model/scaler selection, full-precision evidence and output formatting retain their existing meaning. Model identity remains tied to the bytes actually verified and loaded.
  6. Ordinary successful Jobs do not exhaust a lifetime allocation counter or accumulate unbounded handles, processes, source files or diagnostic history.
  7. One documented deployment workflow remains after cutover. Obsolete production launchers, selectors, tests and guidance are removed, with historical rationale preserved.
