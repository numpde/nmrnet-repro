Provider-core tests

Choose the smallest maintained command that exercises the behavior you changed. A protocol test, native calculation and deployed API Job establish different facts. Reuse existing numerical evidence when the model and scientific path have not changed.

Test layout and isolation

The reusable package tests live in packages/provider-core/tests. Unit tests exercise contracts and controlled failure boundaries; contract tests inspect the installed wheel and pinned API artifacts; integration tests join real local transports, SQLite storage and process owners. Normative tests state required behavior; adversarial tests challenge identity substitution, limits, privacy and interruption. Tests of a failure must preserve its actual effect and uncertainty, rather than merely expect an exception.

NMRNet binding tests live separately under tests/integration/provider_core. They consume the installed core together with the binding's source. Both test groups run through Docker-backed Make commands and isolated installed environments. Package tests do not acquire consumer source imports. Tests are excluded from the runtime wheel.

Scientific and deployed API evidence

The opt-in make test/integration/provider/deployment commands exercise installed serial runners and the production factory in Compose. Scientific cases use RDKit and released NMRNet inference; model/API peers can be scripted and local. Read the operator guide for each command's actual inputs, resource needs and proof boundary before starting it.

A real API qualification creates a persistent Job and runs science. When a Job already exists and only result readback failed, use the maintained paired JOB_RECEIPT and JOB_IDENTITY readback mode for that same Job. Do not create another Job or repeat a model run to repair observation or delivery. GUI rendering is outside this repository's system under test.

The deployment record identifies the actual source, images, Job and result bytes behind the shared-delivery witness. The follow-up record distinguishes resolved work from deferred qualification. A command listed here describes its intended test boundary; dated run results establish which revision passed. No single green lane qualifies every interruption, workload or multi-provider deployment.
