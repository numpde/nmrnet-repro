Provider operation and configuration

This reference is for the developer or operator running the provider. For inputs, units, per-atom results and scientific limits, start with the scientific guide.

Provider startup configuration

The binding's result schema is nmrnet.coordinate_shifts.result.v2. Submission instructions may request low, medium or max verbosity and 1–17 significant digits; the defaults are medium and 4. Interpretation records, warnings and scientific limitations remain at every level. Medium includes both coordinate representations; max adds the software-file manifest. The selected output object is frozen before scientific execution. The provider encodes the final API request once and hands those exact bytes to the shared delivery service. Delivery retries preserve the request body; they do not rerender results with new defaults. Source: result planning and publication projection.

The API/GUI provider description is the entry point to the scientific guide. Include its URL in the configured service.description, for example:

NMRNet++ predicts per-atom H/C chemical shifts from 3D molecular coordinates. Scientific guide, limits, references and source: https://numpde.github.io/nmrnet-repro/

Set the description in the deployment's startup configuration. The maintained operator example also supplies the offering text shown to scientific API/GUI readers: supported inputs, per-atom ppm output, hydrogen handling, separate geometries and the scientific guide. Copy and adapt that TOML; the runtime transports the operator's admitted text. nmrnet_provider.service.ProviderService publishes the admitted description through Provider Hello; operators retain ownership of their configured text. This follows SECS's explicit provider-description example and NMRPeak's announcement description.

The internal nmrnet_provider.config.load_provider_config loads one explicit UTF-8 TOML file, up to 64 KiB, into the existing runtime policies. It reads the configured credential, interpreter keys and TLS roots before any HTTP request, native operation or network acquisition. Run its focused, offline container tests with make test/integration/provider-core/config.

Deployment installation derives api, delivery.socket_path and delivery.socket_group_id from the selected shared binding. The table below describes the generated runtime configuration; keep those derived fields out of the authored provider definition.

Installation writes that runtime file under secrets/deployments/<name>/bundles/generation-*/config/provider.toml. Change the authored inputs and reinstall; do not edit a sealed generation.

The runtime file requires schema_id = "nmrnet.provider.runtime_config.v1" and these closed tables; unknown fields fail startup:

interpreter max_turns, ordered [[interpreter.endpoints]] none

Paths are absolute container paths. Startup inputs must be regular files without a final-component symlink. Secrets must belong to the container user and have mode 0400 or 0600; configuration and CA files must belong to root or that user, with no group or other write permission. Parent mounts remain host-controlled. Keys and signing credentials are limited to 16 KiB each; CA files to 1 MiB. Interpreter keys allow one final LF or CRLF; other whitespace is rejected. The API-issued signing credential must match the intended profile and provider. Set API topology explicitly to dev-local, dev or web; it is a different vocabulary from credential profiles (dev-local, dev, run). Every API reply must carry the matching environment marker. Valid header request IDs remain available for authorized diagnostics when a reply is malformed or interrupted; they establish neither acceptance nor a safe retry. Endpoints, models, identities and budgets have no guessed deployment defaults. Generation's cooperative timeout must be below its channel deadline. Job states are an explicit nonempty selection of open and closed; cancelled Jobs stop work. Service presentation is validated before runtime resources are opened. The analysis kind remains the implemented peaks_from_mol; it is not a configuration selector. source_seconds controls the supplied-coordinate reader channel. SMILES generation uses preparation.generation_seconds. These waits do not change the host's worker isolation, resource ceilings or accepted generation settings.

Each HTTP role uses verified system roots unless ca_file supplies replacement roots. Explicit CA bytes are read once and used directly, including when a path changes afterward. Empty or malformed CA files fail; they never select system roots. Ambient SSL_CERT_FILE, SSL_CERT_DIR and SSLKEYLOGFILE are rejected. The analysis kind is the code-owned peaks_from_mol offering, following G01's identity. source_sha256 identifies only the consumed TOML bytes, not key/CA contents or the complete qualified runtime. Owned error explanations remain public; original file/parser evidence and independent close failures remain protected causes.

This ports SECS's closed configuration and descriptor reader, using NMRPeak's existing policy construction. The port retains causes without exposing private paths, completes short reads, checks secret permissions, and binds TLS trust to the admitted bytes. The ambient TLS rules follow the pinned runtime's CPython 3.12.12 SSL implementation.

Launching the provider

The contained foreground entrypoint is python -m nmrnet_provider.process with required --config, --execution, --models and --diagnostics paths, plus --api-proxy-socket, --interpreter-proxy-socket and --store-proxy-socket. Every foreground HTTP role uses its explicit Unix route; omission or an invalid socket path refuses startup before retained storage or network acquisition. Its installed image is built and checked through the lanes below. Execution and model declarations are bounded to 64 KiB each and admitted before storage, HTTP or native allocation. Execution requires exactly image_id (prediction), geometry_image_id, controller_image_id, repository_revision, upstream_revision, runtime_identity_source = "caller" and nonempty tool_sources. Image IDs use sha256: plus 64 lowercase hexadecimal characters; revisions use 40. Source names are canonical repository-relative paths with exactly integer size and lowercase sha256; empty source files are permitted. These are caller-declared identities, not independently observed image or source-closure attestations. The process adds observed execution_declaration_sha256, prediction_declaration_sha256 and startup_configuration_sha256; callers cannot override them. Model declarations use the released selection. Results contain only dictionary and H/C checkpoint/scaler member names, positive sizes, SHA-256 and their archive SHA-256. Archive acquisition metadata is excluded; other unknown fields are refused. Scientific model-byte verification stays with the native owner.

The provider's private deployment.toml declares interpreter and Upload-store routes. The shared binding supplies the API route. Each route selects local (a frozen address on an observed internal Docker network), mapped (an explicit host-network IPv4 destination), or external (interface-bound DNS). Each requires an explicit interface and log_level: INFO, DEBUG or WARNING. Mapped/local addresses preserve the configured hostname and port for TLS and signing; they do not fall back to DNS. External interpreter/store routes use the provider settings' resolvers; an external API route uses the binding's resolver_file.

Setup downloads use WLAN_INTERFACE. Running services use the explicit interfaces in their route definitions. The choices may be the same or different; neither supplies the other. See the provider route example and shared binding example.

Persistent deployment

A named deployment uses Docker Compose and unless-stopped restart policy. Its seven containers are the provider, three serial native runners (prediction, structure reader and conformer generator), and three proxies (API, interpreter and Upload access). The up command finishes after checking their configuration and current readiness. Docker must itself start after a host reboot. A separate shared delivery service on the same Docker host owns outstanding completion and failure requests. It can finish delivery while a provider is stopped or being replaced. On restart, the provider reconciles its small control checkpoints with the delivery service and API; it never repeats prediction to recover a result. Unresolved execution or conflicting identities require operator diagnosis. Sources: service admission and recovery and native retirement barriers. Keep the public provider definition in config/deployments/<name>/provider.toml and private machine settings in config/deployments/<name>/deployment.toml. Copy the latter from the deployment settings example. Use mode 0644 for the caller-owned public definition and 0600 for private machine settings; neither may be writable by group or others. Keep the path and network settings in that private deployment definition. The producer's checkpoint database uses a provider-only Docker volume; final request bodies use the delivery service's separate queue volume.

Keep interpreter keys and provider TLS files in secrets/deployments/<name>/, named as in the provider definition. Keep the host's binding definition as an operator-owned configuration file and its credentials as separate secret files, following the shared deployment instructions. The binding names the exact API credential and optional CA files. Private directories require mode 0700 and secret files 0400 or 0600, owned by the deployment caller. Shared delivery mounts only the exact configuration, credential and trust inputs it needs, read-only. Its queue, IPC sockets and proxy runtime directories use Docker volumes. It creates no persistent host deployment directory or generated configuration tree.

Build or load the NMRNet controller, geometry and inference images and the shared runtime image first. Use the same binding definition for both deployment owners; select NMRNet's binding by name. No separate API block or socket grant belongs in the provider definition.

provider/prepare records the three NMRNet image IDs under .work/provider/, .work/preparation/ and .work/inference/. Install admits those image records and captures the model selection from artifacts/prediction-models.json; up uses the frozen generation.

make -C /path/to/nmr-provider-tools delivery/deployment/up DELIVERY_BINDINGS=/private/bindings.toml SHARED_RUNTIME_IMAGE=sha256:YOUR_SHARED_IMAGE

make provider/deployment/install DEPLOYMENT=<name> DELIVERY_BINDINGS=/private/bindings.toml DELIVERY_BINDING=<binding-name> SHARED_RUNTIME_IMAGE=sha256:YOUR_SHARED_IMAGE
make provider/deployment/up DEPLOYMENT=<name>
make provider/deployment/status DEPLOYMENT=<name>
make provider/deployment/logs DEPLOYMENT=<name>
make provider/deployment/down DEPLOYMENT=<name>

Install freezes a new input generation and refuses replacement while that provider is running. Up initializes the producer's checkpoint volume, starts the proxies and serial native runners, then waits for provider readiness, including an accepted API Hello. This establishes readiness, not scientific accuracy or successful model interpretation. Down stops that provider and its dependencies; it leaves shared delivery and its queue available.

make -C /path/to/nmr-provider-tools delivery/deployment/status PROJECT=<project-name>
make -C /path/to/nmr-provider-tools delivery/deployment/logs PROJECT=<project-name>
make -C /path/to/nmr-provider-tools delivery/deployment/down PROJECT=<project-name>

PROJECT is the project value in the binding definition. Status, logs and down inspect that project's actual Docker containers; they do not need a generated host recipe. Up derives the recipe from the operator's inputs and requires the project to be stopped. Keep its referenced input files available.

One shared service can serve several providers. Its complete binding definition and stable project identify the host service. Stopping it retains its queue and IPC volumes; its API routes belong to that shared deployment.

Update and redeploy

From a clean checkout on the Docker host, using the deployment owner's account:

git switch main
git pull --ff-only
git submodule update --init --recursive

Prepare NMRNet's three images and model files using the selected shared image for setup transport. Wheelhouse and setup interface are chosen once:

make provider/prepare WHEELHOUSE=/path/to/shared-wheelhouse WLAN_INTERFACE=YOUR_SETUP_INTERFACE SHARED_RUNTIME_IMAGE=sha256:YOUR_SHARED_IMAGE

For a provider-only update, stop NMRNet, install its new generation from the existing binding definition, and start it. Shared delivery can continue publishing acknowledged results throughout:

make provider/deployment/down DEPLOYMENT=<name>
make provider/deployment/install DEPLOYMENT=<name> DELIVERY_BINDINGS=/private/bindings.toml DELIVERY_BINDING=<binding-name> SHARED_RUNTIME_IMAGE=sha256:YOUR_SHARED_IMAGE
make provider/deployment/up DEPLOYMENT=<name>

For a shared-service replacement, coordinate all producers using it, inspect outstanding work, stop the incumbent owner, then start the shared owner with the complete binding definition and existing queue/IPC identities. Do not run two delivery owners or discard unresolved data to complete an update. Container removal removes its bounded Docker logs; collect needed diagnostics before stopping it. See delivery ownership and API qualification.

Routine logs and private diagnostics

The provider, native runners, proxies and shared delivery service send stdout and stderr to bounded Docker logs: json-file, three files of at most 10 MiB each per container, with a 1 MiB nonblocking delivery buffer. A stalled sink may drop messages; old files rotate. Container removal deletes its logs; read bounded logs before stopping or reconfiguring a deployment. There are no parallel application log dumps.

make provider/deployment/logs DEPLOYMENT=<name> reads the latest 80 messages per retained component. Logs may include native tracebacks, molecular inputs and completed predictions after a failed reply; restrict Docker access. Scientific results belong to the API after confirmed publication; outstanding request bodies belong to the delivery queue. Missing log messages do not prove that a request failed or that work retired. The historical journald qualification in note 019 does not qualify this Compose logging configuration. Docker documents rotation limits and nonblocking delivery.

Result delivery and storage

The provider decides whether a scientific outcome is suitable for publication and encodes its final completion or failure request. It sends those bytes over its configured Unix socket to the shared service. The service commits them to its private SQLite queue before acknowledging the handoff. Its signing identity and API destination come from deployment configuration, not the submitted body.

The provider can release its in-memory result after that acknowledgement. The service delivers the unchanged body, with fresh request signing and capped backoff for permitted retries. A verified matching API receipt removes the queued body. Completed results are available through the API; the provider keeps no completed-result archive, per-Attempt result file or transcript history.

The producer keeps only small recovery checkpoints: the original START identity, API admission, execution-entry digest, selected request digest and handoff or suppression facts. It clears them after the relevant handoff or terminal API observation and confirmed native cleanup. A terminal API observation closes lifecycle uncertainty; it does not prove that a particular candidate result was accepted.

The delivery queue has explicit item and byte allowances for each provider. Held items still count against that allowance. A full queue pauses fresh computation; a result already selected for handoff waits and retries the same bytes. Native cleanup proceeds independently of delivery. Unconfirmed cleanup prevents another scientific execution, while an approved result can still reach the API.

After a restart, the service resumes committed queue entries. The provider uses its scoped relay inventory and API observations to reconcile control metadata, and excludes relay-owned Jobs from new computation. If a producer dies before durable handoff, a result held only in memory can be lost. An absent queue row never authorizes another prediction. Preserve unresolved identities and diagnose them through the API and Docker logs.

Storage and recovery owners: pending queue, producer checkpoints, recovery without scientific replay. The design and existing evidence are in note 021; deferred refinements and further testing are tracked in note 022.

Checking API delivery

Reconciling held delivery data

A held item has no verified matching API receipt. Resolve the reported cause and remote Attempt before deciding to discard its local payload. First explicitly stop shared delivery; this affects all bindings on this Docker host. Listing and discard run offline under the queue's existing exclusive lock and refuse while the daemon owns it. They never stop or restart the service automatically.

make -C /path/to/nmr-provider-tools delivery/deployment/down PROJECT=<project-name>
make -C /path/to/nmr-provider-tools delivery/deployment/held DELIVERY_BINDINGS=/private/bindings.toml SHARED_RUNTIME_IMAGE=sha256:YOUR_SHARED_IMAGE API_ORIGIN=<exact-origin> PROVIDER_REF=<provider-ref>
make -C /path/to/nmr-provider-tools delivery/deployment/discard DELIVERY_BINDINGS=/private/bindings.toml SHARED_RUNTIME_IMAGE=sha256:YOUR_SHARED_IMAGE API_ORIGIN=<exact-origin> PROVIDER_REF=<provider-ref> EXECUTION_ATTEMPT_REF=<attempt-ref> BODY_SHA256=<held-digest>
make -C /path/to/nmr-provider-tools delivery/deployment/up DELIVERY_BINDINGS=/private/bindings.toml SHARED_RUNTIME_IMAGE=sha256:YOUR_SHARED_IMAGE

The list shows only the selected binding's held metadata and reason, without payload bodies or a dump file. Discard requires that exact binding, Attempt and digest and removes only a held row; pending rows remain unchanged. It proves neither API acceptance nor resolution of the remote Attempt. Producer sockets have no deletion route. Source: offline operator command and queue disposition owner.

One scientific Job

The prediction targets create one persistent Job on the selected API. Pasted targets use fixed supplied chloromethane and compare against an existing pinned scientific receipt; generated-SMILES targets check received generation provenance and H/C coverage without an independent shift-value oracle. These targets are excluded from offline test aggregates:

To check an already installed deployment, use make provider/qualify/api/existing-pasted with explicit DEPLOYMENT, PROJECT_REF, USER_ID, CLIENT_CREDENTIAL_DIRECTORY, CA_FILE, ADDRESS, INTERFACE, OUTPUT, API_CLIENT_IMAGE and RETAINED_RESULT. The client directory must contain the entitled user's registration.json and signing.private.json; the provider key does not authorize user Jobs. Select the historical pasted oracle at the absolute path to artifacts/pasted-scientific-oracle.json as RETAINED_RESULT. Output, credential and CA paths must also be canonical absolute paths.

This lane creates only one finite public client. It derives API, provider, interpreter and current prediction-image expectations from the admitted original deployment; it neither launches a second provider nor opens its Attempt store. Its received result must match the unchanged numerical oracle and the current image pin. Configured correction/fallback is accepted within its existing turn budget; actual turns, corrections and routes stay in the retained result. Use a fresh private OUTPUT, including an ignored qualification leaf if desired. Failed or uncertain submissions are retained and never resubmitted automatically.

If the Job was created but client readback stopped, supply JOB_RECEIPT=/absolute/path/to/original/client/created.json and JOB_IDENTITY=/absolute/path/to/original/source/identity.json to the same existing-pasted target, with a fresh OUTPUT and the original client, project, network and oracle selectors. DEPLOYMENT is unnecessary in this mode. Expected execution comes from that original capture, so readback still works after redeployment or producer shutdown. It performs GET requests for that original Job only; it does not create, select or open another Job, or repeat prediction. The received result cannot supply its own expected image identity.

  • make provider/qualify/api/pasted uses the isolated scripted model peer.
  • make provider/qualify/api/real-pasted uses one explicitly selected real endpoint.
  • make provider/qualify/api/real-smiles requests one generated CCl conformer through one explicitly selected real endpoint.
  • make provider/qualify/api/real-smiles-multiple requests three generated CCCC conformers and checks each geometry's provenance and H/C coverage.
  • make provider/qualify/api/real-upload attaches an XYZ file and compares its supplied atoms and predictions with the pinned scientific fixtures.
  • make provider/qualify/api/real-sdf-zip publishes one ZIP containing the authored two-record, carbon-only SDF and creates one API Job. It compares both geometries and eight carbon shifts exactly with the retained R46 result, while checking the new Upload's separate archive/member identities. Its readback, process and host budgets are 900, 1200 and 1220 seconds. This does not exercise browser submission. An uncertain transfer must be reconciled using the original Upload. After its storage owner confirms absent bytes, pass UPLOAD_RECEIPT=/absolute/path/to/original/client/upload-created.json with a fresh OUTPUT to continue that reservation without creating another Upload. A null finalization hash alone does not prove absent bytes. This explicit continuation checks the live identity/state and requests a fresh capability; it does not recover the old capability or retry a transfer automatically. Omitting UPLOAD_RECEIPT creates a new reservation.

Command-line selectors for these targets are:

  • API_ORIGIN, TOPOLOGY, PROJECT_REF and USER_ID: the operator's chosen API, expected topology and entitled client/project. Provider identity and credential profile are read from the API-issued JSON file selected by PROVIDER_CREDENTIAL.
  • PROVIDER_CREDENTIAL, CLIENT_CREDENTIAL_DIRECTORY and CA_FILE: absolute paths to the issued provider key, the client's original registration/private pair and the API trust certificate. Keys must remain caller-owned and mode 0400/0600.
  • ADDRESS and INTERFACE: the observed publication's literal IPv4 destination and explicit host interface. The configured origin/port stays unchanged for TLS and signatures. No DNS or direct fallback is attempted.
  • API_CLIENT_IMAGE: an immutable local API runtime image ID containing the API-owned credential validator/signing example. No implicit pull or installation.
  • PROVIDER_TOOLS, SHARED_RUNTIME_IMAGE and WHEELHOUSE: the shared owner's checkout, its immutable runtime image, and the cache containing the pinned core source archive. Temporary qualification deployments use that owner's normal commands with an isolated binding definition and project.
  • RETAINED_RESULT: an absolute path to the existing scientific comparison receipt; its expected hash remains pinned in the fixture client. It is never regenerated from this run's predictions.
  • OUTPUT: a fresh absolute private directory outside the checkout, separate from all credential/trust inputs. It retains configuration and protected receipts. Producer checkpoints and outstanding terminal bodies remain in the recipe's named Docker volumes. Preserve both the directory and those volumes; inspect them before any new mutation after failure.

The scripted target additionally requires LOCAL_NETWORK and LOCAL_INTERFACE for its peer's observed internal network. The real targets instead require:

  • INTERPRETER_CONFIG: an absolute path to a private TOML fragment containing only [interpreter] and exactly one [[interpreter.endpoints]] entry. Its key must be in the separate key_file; optional ca_file supplies model trust roots.
  • EXTERNAL_INTERFACE and RESOLVERS: the explicit model-egress interface and space-separated literal IPv4 DNS resolvers. These remain separate from the API publication's ADDRESS/INTERFACE.

Each real target first inspects fragment metadata without a key grant. It then grants only the referenced individual key/optional-CA files to offline staging, uses the existing configuration admission, and freezes their exact bytes under the private output. It selects no fallback endpoint and starts no scripted peer. The existing foreground host and native launchers own execution and retirement; no API signing credential or provider configuration is sent to the model.

Real staging sets the preparation budget to 240 seconds. Each profile defines its expected interpreter operations, scientific comparisons and confirmed-cleanup requirements in the API fixture client. A result can therefore have been accepted by the API even when the target exits nonzero and writes no client/passed.json.

Diagnostics and shutdown

Diagnostics require an absolute directory, mode 0700, owned by the container user. Process readiness uses expiring status observations tied to the current process identity. Causal error reports go to stderr/Docker logs without a file fallback. SIGINT/TERM stops new work and requests bounded settlement. If an original borrower remains active, the process reports requires_host_retirement = true, keeps its original owners alive and waits for the host to retire it; a normal stop signal does not cancel the same work again. An unadmitted diagnostics directory receives no files; safe reasons or OS errno still reach Docker's stderr logging. Neither diagnostics nor the readiness observations establish successful science. Run the focused subprocess proof with make test/integration/provider-core/process.

Execution failures include the acknowledged Job and Attempt references in the protected report. Native setup can fail before an Attempt exists; when a Job was already selected, that setup failure reports its Job reference alone. Source-only setup without Job context leaves those references absent. These fields identify affected work; they do not establish dispatch or acceptance of a result.

Images and network isolation

To acquire the provider dependencies and model files and build its three images in one invocation:

make provider/prepare WHEELHOUSE=/path/to/shared-pool WLAN_INTERFACE=YOUR_SETUP_INTERFACE SHARED_RUNTIME_IMAGE=sha256:YOUR_SHARED_IMAGE

Omit either selection to choose it once on the terminal. The command runs the existing owners in sequence and stops on failure. It reuses cached downloads and keeps existing extraction trees with their receipts; selected model bytes are checked against pinned hashes by the provider before decoding. It requires the initialized upstream submodule and the pinned Python base, provisioned with make packages/base-images/python/download. That explicit bootstrap uses Docker daemon routing. Build/load the shared runtime through nmr-provider-tools. API/interpreter credentials and service configuration are subsequent steps.

Build and check the installed controller offline:

make test/unit/provider/image
make provider/image/build WHEELHOUSE=/path/to/shared-pool
make test/integration/provider-runtime

The build uses committed input bytes and the released core wheel and locked runtime dependencies selected from the shared WHEELHOUSE root. It first requires the pinned Python base locally; it never downloads a missing base. The resulting image contains a wheel-installed provider-core and image-owned binding modules in an isolated, pip-free environment. Startup requires no source or wheel mounts and installs nothing. The recorded immutable image ID and committed-input label are checked before image tests. /opt/provider/dependency-inputs.json retains lock and wheel hashes from pip's actual installation reports; the source/lock label alone does not identify those platform-wheel bytes. Installed-image checks cover the full dependency set, native signing, import origins and isolated CLI startup. They contact no API or model and perform no prediction.

The service network components have focused offline checks:

make test/integration/provider/proxy WHEELHOUSE=/path/to/shared-pool

The controller's HTTPS transport can use a fixed Unix CONNECT socket. The service proxy admits only explicitly granted DNS-name/IPv4 authorities before resolution or connection. Local routing requires a complete frozen host-to-IPv4 mapping; external routing uses the existing explicit interface binding. Both preserve destination TLS. IPv6 literal destinations are refused. The proxy receives no API/model credentials. These checks cover policy, private listener startup, diagnostics and actual loopback TLS. The host launcher must still bind those components to the intended networks and confirm exact container retirement; these component tests establish neither deployment nor external model access.

Attempt and service ownership

nmrnet_provider.runtime.assemble_attempt connects these settings to the existing input interpreter, source acquisition, NMRNet session and core controller. The caller selects a Job from signed ProviderAPI.jobs, opens the scoped store and supplies the prediction allocation and reader/generator factories. Assembly refuses outstanding retained obligations before constructing source/model owners; recovery stays explicit. The returned controller must run the same pending start. Successful return transfers the supplied allocation to that controller, including cleanup if it is never run. Refusal leaves allocation cleanup with the caller. The caller retains lifecycle API/store ownership and must settle any interrupted inventory read before reuse. All HTTP roles have separate transport owners.

The controller selects the final request before handoff. Native retirement and delivery are independent: a cleanup failure holds worker reuse, while the approved request can still be delivered. Every session receives an explicit preparation owner; production supplies the configured interpreter and source readers before the shared scientific execution and delivery path.

nmrnet_provider.service.ProviderService coordinates one Attempt at a time: retained-work/capacity and live-inventory checks precede Hello, fresh discovery and allocation. Verified relay-owned Attempts do not block unrelated Jobs, and those Jobs are excluded from new computation. It refreshes the current announcement through independent I/O, drains or cancels original work on stop, and retains unsettled tasks/controllers. Startup acceptance does not establish scientific readiness.

Startup admission and idle discovery automatically retry reviewed GET failures after the original API I/O retires. Each retry repeats complete admission and discovery from the first page, before allocating work. Initial and periodic Hello announcements also recover from reviewed availability failures: each send rebuilds the latest complete announcement, including changed or withdrawn offerings. The first accepted Hello still gates discovery and allocation; a periodic Hello outage does not cancel an active prediction. The initial delay is service.idle_seconds; it doubles after each failed cycle, capped by the required service.api_backoff_max_seconds, which must be at least idle_seconds. Each actual wait is randomly selected between half and all of that delay. A complete successful read cycle or accepted Hello resets its own backoff. Requests keep their configured deadlines; an outage may wait until recovery or stop, and stop interrupts the backoff wait. A startup request already in flight still has its exchange/retirement deadlines.

Safe reads and fresh complete Hello announcements can recover after rate limits and HTTP 500, 502, 503 or 504, without treating an unverified error body as API authority. The verified API refusals request_body_timeout (HTTP 408), authentication_window_closed and signature_expired confirm that this request did not run; earlier unanswered requests remain unresolved. Existing operation owners may retry with a fresh signature after transport retirement: service reads and Hello keep their paced, stop-responsive retry loops; retained writes keep their own route, command and recovery-window checks. These read and Hello permissions exclude invalid credentials, future-dated signatures and reused nonces. Explicit wrong environment, malformed success, storage/ownership errors and admission holds still stop. Sources: API timing-refusal contract, body-timeout refusal, this-send effect policy and operation-specific retry permissions.

Shared delivery retries retained completion and failure requests after rate limits and recognised API authentication or authorization refusals, as well as network and gateway failures covered by its retry policy. Each attempt preserves the request body and uses a fresh signature. Capped exponential backoff includes jitter; a valid Retry-After adds a minimum wait before that jitter. Stop interrupts the wait. Repeated refusals remain visible in Docker logs: check the reported credentials, clock or API permissions. A matching API receipt clears the queued body; durable local acceptance alone does not establish API publication. Conflicting outcomes remain held; trust, storage and ownership failures require operator attention. Sources: terminal replay permissions, delivery pacing and receipts and HTTP Retry-After.

Active Attempt observations also recover within the required finite lifecycle.observation_gap_seconds window. Each fresh-observation wait includes exchange-lock acquisition, reads, transport retirement and backoff. Its initial delay is the smaller of lifecycle.poll_seconds and service.api_backoff_max_seconds, then doubles with the same half-to-full jitter and cap, clipped by remaining time. The original interpretation or prediction may continue during that window; another phase or an accepted result still requires a fresh allowed observation. A reply that arrives after the window cannot grant that permission.

Window expiry starts scientific retirement independently of HTTP cleanup. The original read remains owned until it settles; neither elapsed time nor requested cancellation proves that work stopped. Expiry, observed server stop and other active Attempt failures still stop the service; preserve unresolved control identities and settle their original owners before restart. No allocation, Attempt mutation or science is retried by the read loop. A Hello receipt confirms the new announcement, without resolving whether an earlier send was accepted. Between settled Jobs, the provider clears handed-off control metadata after cleanup.
