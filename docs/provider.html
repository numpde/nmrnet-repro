Provider operation and configuration

This reference is for the developer or operator running the provider. For inputs, units, per-atom results and scientific limits, start with the scientific guide.

Configuration · Persistent service · Logs · Recovery · API qualification · Interpreter format choices

Provider startup configuration

The binding's result schema is nmrnet.coordinate_shifts.result.v2. Submission instructions may request low, medium or max verbosity and 1–17 significant digits; the defaults are medium and 4. Interpretation records, warnings and scientific limitations remain at every level. Medium includes both coordinate representations; max adds the software-file manifest. The selected output object is frozen before scientific execution and retained with the Attempt. Completed result bytes are replayed exactly; reopening a store does not rerender them with new defaults. Source: result planning and publication projection.

The API/GUI provider description is the entry point to the scientific guide. Include its URL in the configured service.description, for example:

NMRNet++ predicts per-atom H/C chemical shifts from 3D molecular coordinates. Scientific guide, limits, references and source: https://numpde.github.io/nmrnet-repro/

Set the description in the deployment's startup configuration. The maintained operator example also supplies the offering text shown to scientific API/GUI readers: supported inputs, per-atom ppm output, hydrogen handling, separate geometries and the scientific guide. Copy and adapt that TOML; the runtime transports the operator's admitted text. nmrnet_provider.service.ProviderService publishes the admitted description through Provider Hello; operators retain ownership of their configured text. This follows SECS's explicit provider-description example and NMRPeak's announcement description.

The internal nmrnet_provider.config.load_provider_config loads one explicit UTF-8 TOML file, up to 64 KiB, into the existing runtime policies. It reads the configured credential, interpreter keys and TLS roots before any HTTP request, worker allocation or journal acquisition. Run its focused, offline container tests with make test/integration/provider-core/config.

The file requires schema_id = "nmrnet.provider.runtime_config.v1" and these closed tables; unknown fields fail startup:

Table Required fields Optional fields
api origin, profile, topology, provider_ref, credential_file, exchange_seconds, retirement_seconds ca_file
interpreter max_turns, ordered [[interpreter.endpoints]] none
each endpoint configuration_id, url, model, key_file, request_bytes, response_bytes, exchange_seconds, retirement_seconds ca_file, reasoning_effort
uploads store_origin, per_source_bytes, total_bytes, requests, seconds, exchange_seconds, retirement_seconds ca_file
preparation seed, max_iterations, timeout_seconds, generation_seconds, max_worker_calls, seconds none
lifecycle consumer_id, generation_id, store_root, maximum_records, confirmed_history_records, filesystem_reserve_bytes, store_seconds, allowed_job_states, poll_seconds, task_settle_seconds, observation_gap_seconds, start_retry_window_seconds, terminal_retry_window_seconds none
service display_name, description, offering_description, page_size, maximum_pages, idle_seconds, api_backoff_max_seconds, hello_seconds, drain_seconds, settle_seconds, allocation_seconds, prediction_seconds, source_seconds none

Paths are absolute container paths. Startup inputs must be regular files without a final-component symlink. Secrets must belong to the container user and have mode 0400 or 0600; configuration and CA files must belong to root or that user, with no group or other write permission. Parent mounts remain host-controlled. Keys and signing credentials are limited to 16 KiB each; CA files to 1 MiB. Interpreter keys allow one final LF or CRLF; other whitespace is rejected. The API-issued signing credential must match the intended profile and provider. Set API topology explicitly to dev-local, dev or web; it is a different vocabulary from credential profiles (dev-local, dev, run). Every API reply must carry the matching environment marker. Valid header request IDs remain available for authorized diagnostics when a reply is malformed or interrupted; they establish neither acceptance nor a safe retry. Endpoints, models, identities and budgets have no guessed deployment defaults. Generation's cooperative timeout must be below its channel deadline. Job states are an explicit nonempty selection of open and closed; cancelled Jobs stop work. Service presentation is validated before runtime resources are opened. The analysis kind remains the implemented peaks_from_mol; it is not a configuration selector. source_seconds controls the supplied-coordinate reader channel. SMILES generation uses preparation.generation_seconds. These waits do not change the host's worker isolation, resource ceilings or accepted generation settings.

Each HTTP role uses verified system roots unless ca_file supplies replacement roots. Explicit CA bytes are read once and used directly, including when a path changes afterward. Empty or malformed CA files fail; they never select system roots. Ambient SSL_CERT_FILE, SSL_CERT_DIR and SSLKEYLOGFILE are rejected. The analysis kind is the code-owned peaks_from_mol offering, following G01's identity. source_sha256 identifies only the consumed TOML bytes, not key/CA contents or the complete qualified runtime. Owned error explanations remain public; original file/parser evidence and independent close failures remain protected causes.

This ports SECS's closed configuration and descriptor reader, using NMRPeak's existing policy construction. The port retains causes without exposing private paths, completes short reads, checks secret permissions, and binds TLS trust to the admitted bytes. The ambient TLS rules follow the pinned runtime's CPython 3.12.12 SSL implementation.

Launching the provider

The contained foreground entrypoint is python -m nmrnet_provider.process with required --config, --execution, --models and --diagnostics paths, plus --api-proxy-socket, --interpreter-proxy-socket and --store-proxy-socket. Every foreground HTTP role uses its explicit Unix route; omission or an invalid socket path refuses startup before retained storage or network acquisition. Its installed image is built and checked through the lanes below. Execution and model declarations are bounded to 64 KiB each and admitted before storage, HTTP or native allocation. Execution requires exactly image_id (prediction), geometry_image_id, controller_image_id, repository_revision, upstream_revision, runtime_identity_source = "caller" and nonempty tool_sources. Image IDs use sha256: plus 64 lowercase hexadecimal characters; revisions use 40. Source names are canonical repository-relative paths with exactly integer size and lowercase sha256; empty source files are permitted. These are caller-declared identities, not independently observed image or source-closure attestations. The process adds observed execution_declaration_sha256, prediction_declaration_sha256 and startup_configuration_sha256; callers cannot override them. Model declarations use the released selection. Results contain only dictionary and H/C checkpoint/scaler member names, positive sizes, SHA-256 and their archive SHA-256. Archive acquisition metadata is excluded; other unknown fields are refused. Scientific model-byte verification stays with the native owner.

The host entrypoint is make provider/run, with explicit startup paths and route choices. API_ROUTE, INTERPRETER_ROUTE and STORE_ROUTE each select local (an observed peer on an internal network), external (interface-bound DNS), or mapped (an explicit IPv4 destination on the host network). Mapped routes require MAPPED_INTERFACE and MAPPED_ADDRESSES='hostname=IPv4 ...', with exactly the hosts used by those routes. They preserve the configured HTTPS origin and port for TLS and signing and never fall back to DNS. A host-gateway name is not an address: inspect the actual host publication and supply its literal address. EXTERNAL_INTERFACE and RESOLVERS are required only for external; they can use a different interface from the mapped host publication. This follows Magnet's host-gateway localhost route, using this repository's existing interface-bound proxy instead of an ambient host name override. A configured launch profile is distinct from a completed API run.

Persistent user service

Use the existing provider/run host owner through the tracked user-service template. The service does not build images, provision identities or create test Jobs. Prepare the qualified images and a private operator TOML first. Its lifecycle.store_root owns durable Attempt state; the service profile does not introduce another store.

Copy provider-service.env.example outside the checkout, edit its config/source/runs paths and explicit route settings, and set mode 0600. Create its NMRNET_RUNS_ROOT_INPUT as a caller-owned mode-0700 directory. Put key material in the TOML's separate private files, never in this environment file. The installer pins the checkout path itself.

make provider/service/install UNIT=local SERVICE_CONFIG=/absolute/private/provider-service.env
make provider/service/start UNIT=local
make provider/service/status UNIT=local
make provider/service/logs UNIT=local
make provider/service/stop UNIT=local

install copies the profile to ~/.config/nmrnet-repro/local.env, installs nmrnet-provider@.service under ~/.config/systemd/user, and reloads the user manager. It neither starts nor enables the instance. Updating an active instance is refused. This template uses the standard ~/.config location; a different XDG_CONFIG_HOME is explicitly unsupported.

start starts the user-manager unit without replacing a conflicting manager job. status reports manager state and, while its runtime locator exists, the retained installation path. Its startup-admission marker is distinct from API availability. Confirm the provider's actual announcement through the API client. logs reads bounded supervisor messages and uses that locator for the current/last controller's Docker journal. After reboot, a refused startup can occur before that volatile locator is recreated: the supervisor journal names the refused prior installation; use its retained container IDs with provider/logs. Other component IDs use that same command. stop requests asynchronous shutdown; check status until drain completes. It does not treat a request acknowledgement or elapsed time as retirement. Manager requests have a 30-second client deadline; after a timeout, inspect current state before repeating a request.

Each activation uses the systemd invocation ID for a fresh installation below the configured runs root. The host locks that root and refuses another start unless the previous installation has its original host-retired receipt. Unknown/missing evidence requires inspection. The configured Attempt store stays unchanged. Restart=no, SendSIGKILL=no and an unlimited manager stop timeout preserve original drain/retirement ownership, including held failures. Runtime native allocations retain their existing bounded recovery. No whole-service automatic restart or blind scientific replay is added.

Startup at user-manager activation is a separate choice:

make provider/service/enable UNIT=local
make provider/service/disable UNIT=local

Enablement does not start the unit now. Starting before login after boot also requires administrator-enabled user lingering; enable alone does not establish that. No reboot or lingering change is part of ordinary installation.

The lifecycle follows Magnet's named deployment operations and SECS's preserved state/owner-first shutdown; exact donor revisions, systemd contracts and local cutover observations are recorded in note 004.

Routine logs and private diagnostics

Service and native-worker stdout and stderr are collected by Docker's journald driver, including raw tracebacks and scientific exception notes. Standard Python logging supplies routine messages. Owned messages default to INFO; add LOG_LEVEL=DEBUG or LOG_LEVEL=WARNING to the Make launch command to change them. Dependency messages below WARNING stay suppressed. Healthy idle polling is silent.

Read the latest 200 messages for a component or a removed native worker using its full ID from the retained worker.cid receipt:

make provider/logs CONTAINER_ID=<64-character-container-id>

The host must provide journald and journal read access. Launch refuses an unsupported driver; it has no alternate-driver fallback. The 1 MiB nonblocking delivery buffer protects work from a stalled log sink and may drop messages. Host journald settings bound shared retention, so logs may expire before an investigation. Container removal does not itself remove journal entries. Docker documents the driver and full-ID filter and nonblocking delivery.

There are no parallel stdout/stderr dump files. Raw logs can include supplied molecular data and completed predictions retained after a failed reply; access and retention follow the host journal policy. Resource snapshots, scientific results, control and retirement receipts keep their existing owners; absence of a journal message proves none of those outcomes. Startup capture/metadata helpers publish an explicit host-fields handoff file, with both streams going to Docker. Design and qualification are recorded in note 019. The opt-in make test/integration/provider/logging lane qualifies normal, fatal and host-interrupted synthetic processes, including post-removal retrieval and both stdout and stderr without file dumps, without model calls or API Jobs.

Recovering a stopped store

Stop the original host and confirm it has released the store. Preserve its evidence and choose a fresh empty installation root for each recovery command. Keep the TOML and SOURCE_ROOT unchanged, including the configured existing store, scope and API identity. The bounds below are examples, not defaults:

make provider/recovery/inspect \
  CONFIG=/srv/nmrnet/input/provider.toml SOURCE_ROOT=/srv/nmrnet/input \
  INSTALLATION_ROOT=/srv/nmrnet/recovery-inspect \
  MAXIMUM_STARTUP_BYTES=131072 HOST_DRAIN_SECONDS=90

Inspection is offline: it grants only the TOML and retained store, without API credentials, CA files, model keys or worker access. It prints the protected result.json path after cleanup. Set record_sha256 to the exact records[].record_sha256 of one selected record. For this mapped example, set api_interface and api_addresses to your previously verified API-only binding:

make provider/recovery/run \
  CONFIG=/srv/nmrnet/input/provider.toml SOURCE_ROOT=/srv/nmrnet/input \
  INSTALLATION_ROOT=/srv/nmrnet/recovery-run \
  MAXIMUM_STARTUP_BYTES=131072 HOST_DRAIN_SECONDS=90 \
  RECORD_SHA256="$record_sha256" API_ROUTE=mapped \
  MAPPED_INTERFACE="$api_interface" MAPPED_ADDRESSES="$api_addresses"

The mapped hostname must match the unchanged TOML's API origin. Other route modes use their selectors described above. Run adds only the declared API credential, optional CA and selected API route. Pending terminal commands are replayed exactly; confirmed records send nothing. A read-required terminal record performs one state read and retains that observation; it never resends the terminal command. Already-observed or not-visible records send nothing and remain unresolved: a state read is not a matching receipt for the original result. Entered work is observed without rerunning science. A changed record digest refuses selection. Neither command starts science, deletes records or automatically retries a failure. Unsettled original I/O keeps its owner and lock held for exact host retirement.

local_obligations_settled = true means local records are confirmed; ordinary startup must still pass storage capacity and provider-wide API admission. The isolated regression is make test/integration/provider-service/recovery: synthetic loopback TLS, one exact completion replay and empty-discovery restart, with no real credentials, Jobs, model calls or scientific work. See the recovery entrypoint and R38 and R39 for source and evidence.

Retained history and a full store

lifecycle.maximum_records bounds active storage records. Before fresh admission, the service archives confirmed completions and failures after their controller has returned and released its claim. Clean startup does the same for an entirely confirmed inventory. If any active record is unresolved, the service archives none of its neighbors and holds fresh work. Stop before the complete inventory gate admits no maintenance. Once admitted, the original maintenance batch finishes archive → host native-release acknowledgement → history expiry, including during shutdown. Shutdown observes the same task within its drain and settlement budgets; unfinished work holds its native and storage dependencies. It never starts a replacement batch or repeats science.

Each archive preserves the record's exact original requests, receipts and protected scientific evidence under store_root/history-<scope digest>/ before releasing its active slot. Files remain mode0600 inside mode0700 directories. The core storage contract describes filename lookup and interrupted-copy handling. Recovery inspection lists active obligations; archived confirmations remain available as portable files. An archived key cannot become a fresh Attempt while its record remains.

lifecycle.confirmed_history_records is a required positive integer, for example confirmed_history_records = 64; there is no implicit or unlimited setting. After the matching native-release acknowledgement, the store keeps the newest complete records by API receipt committed_at, with canonical filename breaking ties. It expires older whole records and syncs the history directory before fresh admission. Copy evidence needing longer retention outside store history before expiry. There is no selection exemption within the window; only independent copies and qualification capsules outside it are unaffected. After expiry, the API still owns its public result; local unrounded predictions, exact command bytes and private historical diagnostics are no longer available. Rounded public values cannot reconstruct those original scientific bytes.

Existing history above the configured window blocks ordinary startup and fresh work; startup does not purge it as a migration. Stopped storage inspection can open the bounded archival transition of history plus active slots. A hard crash or failed maintenance may need explicit operator reconciliation; no automatic native-root adoption or uncertain-deletion retry is provided. An ordinary stop lets its original batch finish, so it does not create that excess-history state.

For history limit H, active slots A and record budget R, the logical peak record budget is (H + A + 1) × R, including one complete staging/archive copy. With H=64, A=2 and production R=3,725,916 bytes, that is 249,636,372 bytes (about 238 MiB), before filesystem metadata and the configured reserve. This is a healthy-operation record bound, not a filesystem quota. Native sequence/history release separately removes completed engine/request trees only after its clean host barrier; partial failures preserve remaining evidence and block admission.

History still consumes disk. The provider rechecks space for full outstanding records, a temporary full-record write and filesystem_reserve_bytes, then the complete provider-wide API admission view. These checks reserve no physical blocks. If active obligations or actual disk headroom prevent admission, stop and settle the provider and inspect the retained evidence. Keep the existing store_root, API/provider identity, consumer_id and generation_id; do not discard records or change their scope to make room. Raising a record limit does not settle an obligation, retire a worker or bypass API admission. Separate host native-request limits also apply. The owning capacity check and service admission enforce this behavior.

Checking API delivery

Each opt-in target creates one persistent Job on the selected API. Pasted targets use fixed supplied chloromethane and compare against an existing pinned scientific receipt; generated-SMILES targets check received generation provenance and H/C coverage without an independent shift-value oracle. These targets are excluded from offline test aggregates:

  • make provider/qualify/api/pasted uses the isolated scripted model peer.
  • make provider/qualify/api/real-pasted uses one explicitly selected real endpoint.
  • make provider/qualify/api/real-smiles requests one generated CCl conformer through one explicitly selected real endpoint.
  • make provider/qualify/api/real-smiles-multiple requests three generated CCCC conformers and checks each geometry's provenance and H/C coverage.
  • make provider/qualify/api/real-upload attaches an XYZ file and compares its supplied atoms and predictions with the pinned scientific fixtures.
  • make provider/qualify/api/real-sdf-zip publishes one ZIP containing the authored two-record, carbon-only SDF and creates one API Job. It compares both geometries and eight carbon shifts exactly with the retained R46 result, while checking the new Upload's separate archive/member identities. Its readback, process and host budgets are 900, 1200 and 1220 seconds. This does not exercise browser submission. An uncertain transfer must be reconciled using the original Upload. After its storage owner confirms absent bytes, pass UPLOAD_RECEIPT=/absolute/path/to/original/client/upload-created.json with a fresh OUTPUT to continue that reservation without creating another Upload. A null finalization hash alone does not prove absent bytes. This explicit continuation checks the live identity/state and requests a fresh capability; it does not recover the old capability or retry a transfer automatically. Omitting UPLOAD_RECEIPT creates a new reservation.

Command-line selectors for these targets are:

  • API_ORIGIN, TOPOLOGY, PROJECT_REF and USER_ID: the operator's chosen API, expected topology and entitled client/project. Provider identity and credential profile derive from the admitted provider artifact.
  • PROVIDER_CREDENTIAL, CLIENT_CREDENTIAL_DIRECTORY and CA_FILE: absolute paths to the issued provider key, the client's original registration/private pair and the API trust certificate. Keys must remain caller-owned and mode 0400/0600.
  • ADDRESS and INTERFACE: the observed publication's literal IPv4 destination and explicit host interface. The configured origin/port stays unchanged for TLS and signatures. No DNS or direct fallback is attempted.
  • API_CLIENT_IMAGE: an immutable local API runtime image ID containing the API-owned credential validator/signing example. No implicit pull or installation.
  • RETAINED_RESULT: an absolute path to the existing scientific comparison receipt; its expected hash remains pinned in the fixture client. It is never regenerated from this run's predictions.
  • OUTPUT: a fresh absolute private directory outside the checkout, separate from all credential/trust inputs. It retains configuration, durable Attempt state and protected receipts; inspect them before any new mutation after failure.

The scripted target additionally requires LOCAL_NETWORK and LOCAL_INTERFACE for its peer's observed internal network. The real targets instead require:

  • INTERPRETER_CONFIG: an absolute path to a private TOML fragment containing only [interpreter] and exactly one [[interpreter.endpoints]] entry. Its key must be in the separate key_file; optional ca_file supplies model trust roots.
  • EXTERNAL_INTERFACE and RESOLVERS: the explicit model-egress interface and space-separated literal IPv4 DNS resolvers. These remain separate from the API publication's ADDRESS/INTERFACE.

Each real target first inspects fragment metadata without a key grant. It then grants only the referenced individual key/optional-CA files to offline staging, uses the existing configuration admission, and freezes their exact bytes under the private output. It selects no fallback endpoint and starts no scripted peer. The existing foreground host and native launchers own execution and retirement; no API signing credential or provider configuration is sent to the model.

The maintained profiles use these finite qualification limits, in seconds:

Profile Result-readback budget Whole client process Host observation of client
Scripted 180 240 260
Real pasted or SMILES 900 960 980
Real Upload 900 1020 1040

Real staging sets the preparation budget to 240 seconds. Native prediction prepare, execute and channel closure each have their own 90-second policy; host retirement and API publication are separate operations. A deadline does not prove unsettled work retired: the original owners remain held until release is confirmed. See tools/provider_api_qualification.sh and tests/integration/provider_runtime/{stage_api_config,api_prediction}.py.

Job creation and subsequent mutations are sent once. Failure or uncertainty retains the original requests and receipts; it does not automatically resend a mutation or failed model request. Each profile defines its expected interpreter operations, scientific comparisons and confirmed-cleanup requirements in the API fixture client. A result can therefore have been accepted by the API even when the target exits nonzero and writes no client/passed.json.

Diagnostics and shutdown

Diagnostics require a fresh absolute directory, mode 0700, owned by the container user. The process publishes admitted after startup admission/Hello, and sends causal error reports to stderr/Docker logs without a file fallback. Stopped recovery separately publishes its functional inspect/replay result.json. SIGINT/TERM stops new work and requests bounded settlement. If an original borrower remains active, the process reports requires_host_retirement = true, keeps its original owners alive and waits for the host to retire it; a normal stop signal does not cancel the same work again. An unadmitted diagnostics directory receives no files; safe reasons or OS errno still reach Docker's stderr logging. Neither diagnostics nor the startup marker establish successful science. Run the focused subprocess proof with make test/integration/provider-core/process.

Execution failures include the acknowledged Job and Attempt references in the protected report. Native setup can fail before an Attempt exists; when a Job was already selected, that setup failure reports its Job reference alone. Source-only setup without Job context leaves those references absent. These fields identify affected work; they do not establish dispatch or acceptance of a result.

Images and network isolation

Build and check the installed controller offline:

make test/unit/provider/image
make provider/image/build
make test/integration/provider-runtime

The build uses committed input bytes, the retained core runtime wheelhouse and the locked setuptools wheel. It first requires the pinned Python base locally; it never downloads a missing base. The resulting image contains a wheel-installed provider-core and image-owned binding modules in an isolated, pip-free environment. Startup requires no source or wheel mounts and installs nothing. The recorded immutable image ID and committed-input label are checked before image tests. /opt/provider/dependency-inputs.json retains the frozen dependency inventories; the source/lock label alone does not identify those platform-wheel bytes. Installed-image checks cover the full dependency set, native signing, import origins and isolated CLI startup. They contact no API or model and perform no prediction.

The service network components have focused offline checks:

make test/unit/provider/proxy
make test/integration/provider/proxy

The controller's HTTPS transport can use a fixed Unix CONNECT socket. The service proxy admits only explicitly granted DNS-name/IPv4 authorities before resolution or connection. Local routing requires a complete frozen host-to-IPv4 mapping; external routing uses the existing explicit interface binding. Both preserve destination TLS. IPv6 literal destinations are refused. The proxy receives no API/model credentials. These checks cover policy, private listener startup, diagnostics and actual loopback TLS. The host launcher must still bind those components to the intended networks and confirm exact container retirement; these component tests establish neither deployment nor external model access.

Attempt and service ownership

nmrnet_provider.runtime.assemble_attempt connects these settings to the existing input interpreter, source acquisition, NMRNet session and core controller. The caller selects a Job from signed ProviderAPI.jobs, opens the scoped store and supplies the prediction allocation and reader/generator factories. Assembly refuses outstanding retained obligations before constructing source/model owners; recovery stays explicit. The returned controller must run the same pending start. Successful return transfers the supplied allocation to that controller, including cleanup if it is never run. Refusal leaves allocation cleanup with the caller. The caller retains lifecycle API/store ownership and must settle any interrupted inventory read before reuse. All HTTP roles have separate transport owners.

make test/integration/provider-core/runtime checks signed local discovery through all three interpreted routes, durable publication and ownership failures, with recording scientific ports. It verifies that changed Job input cannot reach the interpreter or native dispatch, and that unconfirmed host retirement blocks publication. These are local wiring tests. Direct coordinate-JSON admission retains its separate existing session binding.

nmrnet_provider.service.ProviderService coordinates one Attempt at a time: retained-work/capacity and live-inventory checks precede Hello, fresh discovery and allocation. Explicit confirmed-history archival precedes capacity checks, outside API retry loops. It refreshes the current announcement through independent I/O, drains or cancels original work on stop, and retains unsettled tasks/controllers. make test/integration/provider-core/service checks this ordering with local TLS and recording workers created inside the allocation factory. Startup acceptance does not establish scientific readiness.

Startup admission and idle discovery automatically retry reviewed GET failures after the original API I/O retires. Each retry repeats complete admission and discovery from the first page, before allocating work. Initial and periodic Hello announcements also recover from reviewed availability failures: each send rebuilds the latest complete announcement, including changed or withdrawn offerings. The first accepted Hello still gates discovery and allocation; a periodic Hello outage does not cancel an active prediction. The initial delay is service.idle_seconds; it doubles after each failed cycle, capped by the required service.api_backoff_max_seconds, which must be at least idle_seconds. Each actual wait is randomly selected between half and all of that delay. A complete successful read cycle or accepted Hello resets its own backoff. Requests keep their configured deadlines; an outage may wait until recovery or stop, and stop interrupts the backoff wait. A startup request already in flight still has its exchange/retirement deadlines.

This applies to safe reads, including selected proxy maintenance responses, without treating an unverified error body as API authority. Credentials, explicit wrong environment, malformed success, storage/ownership errors and admission holds still stop. Active Attempt observations also recover within the required finite lifecycle.observation_gap_seconds window. Each fresh-observation wait includes exchange-lock acquisition, reads, transport retirement and backoff. Its initial delay is the smaller of lifecycle.poll_seconds and service.api_backoff_max_seconds, then doubles with the same half-to-full jitter and cap, clipped by remaining time. The original interpretation or prediction may continue during that window; another phase or an accepted result still requires a fresh allowed observation. A reply that arrives after the window cannot grant that permission.

Window expiry starts scientific retirement independently of HTTP cleanup. The original read remains owned until it settles; neither elapsed time nor requested cancellation proves that work stopped. Expiry, observed server stop and other active Attempt failures still stop the service; preserve retained records, settle the original owners and use the stopped-store recovery procedure before restart. No allocation, Attempt mutation or science is retried by the read loop. A Hello receipt confirms the new announcement, without resolving whether an earlier send was accepted. Between settled Jobs, confirmed records move to private scope-bound history with their original bytes preserved. Unresolved records stay active and block fresh work.

The foreground process emits bounded, redacted api_read_retry and api_read_recovered notices to stderr/Docker logs; Hello uses api_hello_retry and api_hello_recovered. Their latest_hello_send_confirmed flag describes the last sent snapshot's receipt; it does not attest to later supplier or directory state. Their failure evidence describes the preceding failed send. Shutdown reports unconfirmed Hello acceptance through provider_shutdown_observation log records, including stop during initial backoff or a later interrupted send. Pipe notices fit the atomic-write limit; an oversized notice never leaves partial JSON. Notice writes and final error reports do not wait for pipe capacity. The latest failed notice and its output cause remain in memory for shutdown reporting; there is no file fallback. A notice-output failure alone does not terminate the service or change science's outcome. A failed final error write retains original, cleanup and output causes in the owned exception; unresolved work stays held.

Active-read recovery uses api_observation_retry and api_observation_recovered, with the acknowledged Job and Attempt references. Recovery confirms a fresh API observation, not completion or publication; observed server stop still wins. If reporting fails, these notices use the same bounded in-memory diagnostic owner. This observation recovery does not retry mutations. Terminal publication has its own required finite lifecycle.terminal_retry_window_seconds: after science has retired, the controller may replay the same durably retained COMPLETE/FAIL bytes for reviewed availability failures, HTTP 500, or a protocol failure before any verified response head. Each send is freshly signed. Explicit refusals, wrong environment, malformed received receipts, cancellation, failed cleanup and receipt-storage failures do not trigger replay. The same publisher confirms original I/O retirement and rechecks durable command identity before another send.

The terminal retry window starts at the first send failure and includes retirement, diagnostic callbacks and capped jittered waits. No new publisher invocation begins after expiry; one already admitted may finish its existing bounded I/O later. Expiry retains the pending command and protected Job/Attempt/send evidence for stopped recovery. api_terminal_retry and api_terminal_recovered use the same protected notices and failed-output fallback; recovery means the matching terminal receipt was durably retained. These retries never repeat interpretation, geometry generation or prediction. Unreviewed or exhausted condition-report recovery, unreviewed phase-delivery failures and operational deadlines still stop the service; preserve retained records, settle the original owners and follow the stopped-store recovery procedure before restart. The exact replay authority is the retained API contract fixture and its terminal POST x-nmr-recovery/HTTP 500 descriptions, identified in that manifest.

For the fixed preparing and running labels, a reviewed delivery failure can leave progress unconfirmed while this Job proceeds. The service first confirms original API exchange retirement, emits the protected api_progress_unconfirmed notice, and obtains a fresh allowed Attempt/Job observation before dependent work. The notice includes the phase, progress_delivery_confirmed=false, real Job and Attempt references, and safe cause/correlation facts. It does not mean work has continued yet. That read does not confirm progress delivery; no failed label is resent. Authentication, wrong environment, conflicts, malformed received receipts, cancellation and unconfirmed cleanup still stop this path. Session condition reports keep their acknowledgement requirement. Failed notice output uses the existing protected final-report fallback. No extra deadline or retry setting is needed: the fresh read uses lifecycle.observation_gap_seconds and the configured API I/O bounds. The pinned progress PUT's x-nmr-recovery describes why stale progress must not be replayed; see the contract fixture manifest.

An awaited condition update can retry a reviewed temporary delivery failure while that same sequential report is still current. It settles the original exchange before retrying the same body with fresh signing, and dependent work waits for the matching receipt. The retry-admission window starts at the first failed send and uses lifecycle.observation_gap_seconds, including retirement, notices, lock waits and backoff.
