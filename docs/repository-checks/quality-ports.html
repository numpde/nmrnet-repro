Annotations leave raw finding predicates and the scan inventory unchanged. A standalone annotation requires a nonblank explanation after --. The ordinary allow-contract scope is one generic expression on a single-line statement or a single-line condition expression in an If header or a For iterable, one outermost generic expression and its generic children in With context expressions or Assign/Return values (including multiline values), the whole value of a Call-valued Expr, or callable signature defaults. Compound bodies, For/With/Assign targets, and callable decorators, type annotations and bodies remain outside those boundaries. The separate allow-lambda-body tag covers only its immediately following lambda default-result expression at matching indentation. The result must itself be a generic candidate; nested lambdas and ENV/CLI inputs remain strict. Signature, sibling and surrounding findings remain independently visible. The For placement covers only a single-line iterable, including when its body starts on that line. Its target, body and else suite remain visible; this dedicated header placement supports neither multiline iterables nor AsyncFor. The existing single-line statement fallback is unchanged. The dedicated For placement uses the same generic-only, operator-input, one-outermost-expression and no-lambda guards. An annotation before a Return covers its value only; sibling expressions, adjacent statements and any enclosing exception-fallback finding remain visible. A Call-valued Expr covers the callee/receiver and arguments of that one call, including multiline calls, under the same outermost-expression, generic-only, operator-input and no-lambda guards. This supports reviewed consumer invocations, not inferred call purity or assertion semantics. Other multiline Expr values, including bare containers, remain unsupported. Existing single-line statement support is unchanged; this narrow syntax extension does not promise formatting invariance for every expression statement. The discarded ENV-pop tag retains its separate, earlier exact-call boundary.

A dedicated annotation immediately before a literal-key Dict entry covers only that entry's value, including multiline values, under the same one-outermost generic-expression and no-lambda guards. All keys in that Dict must be literal constants; any computed key or unpack entry rejects this placement. Exactly one key AST must start on the next line at the comment's indentation. Multiple key ASTs starting on that line and sibling defaults within the value do not qualify. This is an AST key boundary, not a parser for entry punctuation; parentheses can move a separate literal key's AST start onto a later line. That separate entry remains outside the annotated value. Key expressions, sibling entries and enclosing defaults remain independently visible. ENV and CLI inputs retain the ordinary strict guards. This permits reviewed observation sentinels without treating the containing dictionary as one contract; it does not infer that metadata defaults are safe.

A separate detector correction classifies OR-combined comparison predicates as validation results rather than replacement inputs. Mixed value fallbacks and nested defaults, including ENV get defaults and env["PORT"] or 443, remain findings in their own right. This syntactic distinction does not resolve aliases or overloaded comparisons, prove call purity, or establish that validation is correct or fails closed.

A separate applicability correction retains raw OR findings for composed comparison predicates while admitting only their silent-default finding. Comparison leaves may compose through And, Or and Not in any consumer, including assigned values, returns and call arguments. Bare ENV operands, names, calls and literals used as predicate arms do not qualify. Nested defaults and a function-default finding on the same expression remain independently strict. The existing syntactic limits for aliases and overloaded comparisons still apply.

A separate applicability correction retains raw OR findings but admits an OR consumed only as an If branch truth through BoolOp/Not edges when every operand has a recognized ENV read, an ENV-containing comparison, or such evidence through further boolean edges. Opaque calls and other value consumers do not provide that evidence. This covers independent optional fault activations; assignments, returns, call arguments and ORs consumed by comparisons remain strict. Nested defaults and body findings remain independently applicable.

The existing allow-pop-default tag uses the same explanation and placement checks for one discarded ENV pop call with a literal string key, literal None, exactly two positional arguments and no keywords. Only that call's finding is admitted; consumed values, other defaults and adjacent findings stay strict. This declares idempotent revocation, not a replacement input or outcome.

Recognized ENV reads, raw-argument, argparse and args-attribute rules remain strict. A handler in an ordinary try may be reviewed when it contains only pass, declares specific exception names or dotted names (optionally a flat tuple), and neither its header nor protected suite has recognized ENV/CLI access. Only that handler's finding is admitted. Bare, broad or computed types, except* and return fallbacks remain outside this boundary. Exception aliases are not resolved. The checker enforces annotation placement and expression boundaries; human review judges whether the explanation justifies the default. Test-reference parsing and symbol-existence checks are not required. Subsequent fixes, explicit fixture adaptations and qualified applicability decisions are recorded in note 011.
