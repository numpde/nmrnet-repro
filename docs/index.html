Using the provider

For an API deployment that offers NMRNet++, select peaks_from_mol in its client. Supply one geometry with its units, or plain SMILES with the explicitly requested conformer count, or attach structures and state which records to use and in what order. The configured language-model service receives the submission text and input-selection evidence; it selects preparation tools, while the released NMRNet checkpoints calculate the shifts. Instruction and tool contract · Runtime composition.

The calculation

NMRNet++ extends a 3D neural predictor with semi-supervised training: atom-assigned examples teach individual shifts, while unassigned literature spectra teach matching between predicted and observed shift sets. The published architecture uses an SE(3)-equivariant Transformer with an atom-level regression head. This repository loads released weights; it does not retrain them. The submission interpreter is a separate language model that selects preparation operations. Sources: paper v1, Sections 3.2–3.3, released-weight loader, and input interpreter.

The scientific input is an ordered list of element symbols and three-dimensional coordinates. The selected released H and C models predict chemical shifts in ppm for the corresponding atoms. Other admitted elements remain part of the geometric context. The calculation does not take bond orders, charge, isotope, solvent or temperature as separate prediction features. The exact request fields are coordinate_unit, atoms and coordinates. Sources: request admission and prediction, model tensor construction, and result contract, SCIENTIFIC_LIMITS and GENERATED_LIMITS.

The local selection uses one released fold-0 checkpoint and its paired scaler for each of H and C. H/C heads run sequentially when present, and the returned predictions are sorted by the zero-based atom index within that geometry. Inverse scaling returns the release's ppm convention. A failed required head does not produce a partial scientific result. Sources: exact checkpoint/scaler/archive members and SHA-256 identities, SelectedReleaseModels and release admission, predict_request and _prediction_result, and upstream inverse scaling, pinned revision, lines 75–76.

One request admits at most 128 atoms; a batch admits at most 128 geometries. Byte, result-size and runtime limits may constrain a batch before those count limits. They are software bounds, not a qualified chemical applicability domain. Sources: MAX_ATOMS, MAX_GEOMETRIES, MAX_INPUT_BYTES and MAX_RESULT_BYTES and ResultPlan.

Applicability and experimental comparison

Software admission checks element tokens and finite coordinates; it does not validate that a molecule lies within the model's training distribution. Every atom must have a dedicated token in the pinned release dictionary. Its element tokens are C, N, O, S, H, Cl, F, Br, I, Si, P, B, Na, K, Al, Ca, Sn, As, Mg, Fe, Zn, Cr, Se, Gd, Au and Li; only H/C have selected prediction heads here. Token inventory: reference packet, dictionary.symbols_before_task; selected heads: model declaration, elements. In particular, a successful parse or a 128-atom capacity test is not an accuracy qualification for ions, radicals, metals, unusual bonding or a particular stereoisomer. Sources: require_dictionary_atoms, request admission, and bounded qualification scope.

The paper describes filtered molecular datasets, including removal of radicals and isotope-labelled entries, rather than universal chemical coverage. The local coordinate-only interface does not reproduce those training-data filters as a chemical validity assessment. Sources: paper v1, Section 3.1 and Appendix A and local request fields.

The selected interface has no solvent, temperature or reference-standard parameter and performs no additional experimental-reference calibration. Ppm denotes the released target scale after inverse scaling; it does not establish that your experimental conditions match the data. The paper's solvent-conditioned experiments are a separate model configuration, not a capability implied by these selected H/C checkpoints. Sources: request fields, selected checkpoint names, scaler implementation, and paper v1, Sections 3.4 and 4.3.

Supplied coordinates are not optimized or repaired by preparation. Generated coordinates are estimates from the procedure below. The retained comparisons do not quantify the prediction error due to an inaccurate geometry or the local generator's difference from the paper's optimization procedure. Preserve that distinction when comparing a predicted shift with experiment. Sources: coordinate preparation, generator, and qualification limits.

Supplied coordinates and units

State the coordinate unit in your submission instructions: angstrom, nm or bohr. The provider can also use a supported file format's unit convention. It does not infer units from coordinate magnitudes; if the unit cannot be determined, the input needs clarification. Preparation preserves atom order and does not optimize or repair the supplied geometry. It records the source unit and converts coordinates to angstroms using the factors below. Sources: unit-selection instructions and tools; PreparedGeometry, prepare_rows and coordinate_conversion.

Conversion uses 64-bit floating-point arithmetic (binary64). The predictor then converts the coordinates to 32-bit floating point (float32), rejecting values that cannot be represented as finite numbers. The result includes both the prepared angstrom coordinates and their float32 representation, before the model centers and pads them. Compare these two fields to inspect that rounding step; consult the original input separately to check its decimal text. Sources: _float32_coordinate; compose_net_input; _planned_request, result fields prepared_request and float32_coordinates.

The bohr conversion uses CODATA's recommended central value, whose standard uncertainty is 8.2 × 10⁻¹¹ angstrom per bohr. The nm conversion factor is exact. Both conversions can still incur floating-point rounding: uncertainty in a physical constant and rounding during calculation are separate effects. Preparation records the factor and its reference. The conversion fixtures, “Configured native pasted/Upload lifecycle”, derive binary64 rounding bounds for the fixed nm examples independently of the implementation's output.

Why angstroms?

The selected released H and C models need a coordinate-unit convention, but our review of the NMRNet++ paper v1, release metadata and upstream instructions found no explicit unit statement tied to those model files. The source-review record, “Coordinate-unit evidence gate”, identifies the material examined and the limits of that search.

We use angstroms for these models based on the following evidence:

  1. The upstream geometry helper generates molecular conformations with RDKit and stores their coordinates. RDKit documents conformer bond lengths in angstroms, supporting an angstrom interpretation of these coordinates. Sources: mol2coords, lines 146–192; RDKit GetBondLength.
  2. The upstream preprocessing centers each geometry by subtracting its centroid. This changes the origin without changing bond lengths, so it preserves the incoming coordinate scale. Source: NormalizeDataset, lines 20–26.
  3. We checked two molecules from the released validation data, CH3Cl and CH2Cl2. Treating their stored coordinates as angstroms gives C–H and C–Cl distances within 0.01 Å and 0.04 Å, respectively, of NIST experimental bond lengths. Sources: NIST CCCBDB release 22, Internal coordinates for CH3Cl and CH2Cl2; exact record identities, reference values and tolerance rationale; bond-distance comparison.

The two-molecule comparison supports an angstrom scale and would detect a factor-of-ten error. Its tolerances are local acceptance thresholds, not experimental uncertainties: both released C–Cl distances are about 1.803 Å, compared with NIST values of 1.785 Å for CH3Cl and 1.767 Å for CH2Cl2. This check does not measure chemical-shift prediction accuracy. See the bond-comparison record, “Test meaning and tolerance”.

Together, these observations support our choice of angstroms for model input. They do not establish how every archived or historical training geometry was produced; the upstream helper has not been linked to every such record. The coordinate_unit_decision in the numerical-evidence manifest records the choice and that limitation.

Hydrogens: preserve supplied structures, expand only generated ones

For supplied coordinates, the software neither infers nor adds missing H atoms. It reports the supplied and predicted H counts, while preserving genuinely H-free inputs. Coordinates alone cannot establish whether hydrogens were omitted, partially supplied, or intentionally absent. Missing atoms can also change the predictions for atoms that are present because they change the model's context. Sources: SCIENTIFIC_LIMITS and hydrogen coverage construction and supplied-geometry preparation.

Input situationScientific interpretation
All intended H coordinates suppliedShifts are returned for those H atoms and supplied C atoms.
Some H coordinates suppliedOnly those H atoms receive shifts; this does not establish complete proton coverage.
No H coordinates suppliedNo proton positions or proton shifts are invented; absence is not proof that the molecule is H-free.
Genuinely H-free structureIt remains admissible if the other input/model checks pass.
SMILES plus an explicit conformer countA separate generation step expands the graph with H and generates their coordinates.

The supplied-structure rows follow the result limits and coverage fields; the SMILES row follows _embed and its recorded hydrogen expansion. To obtain complete proton coverage from an incomplete supplied structure, supply the intended H coordinates or explicitly request a separate generation step. Preserving an incomplete geometry is not evidence that its shifts are accurate.

Generated conformers

The SMILES route uses RDKit's ETKDGv3 embedding with recorded seed, iteration and timeout settings. Its parser preserves explicit H atoms; graph expansion adds the remaining hydrogens. The evidence records original atoms/bonds, added-H parent mapping, actual conformer IDs, effective embedding parameters, RDKit version and coordinate-derived stereochemistry. Charge, isotope and graph stereochemistry remain provenance rather than additional model input fields. Source: generate_conformers, _embed, _conformer.

The conformers are the returned embeddings in their recorded order, not an energy-ranked or population-weighted ensemble. RMS pruning is disabled (pruneRmsThresh = -1.0). Original graph-atom indices and added-H parent indices identify the expanded graph across conformers. For supplied Upload records, interpret an atom index within its geometry together with its retained source record and source-position mapping; it is not a global index across files. Sources: embedding_settings and _embed, _planned_geometry and _planned_generated.

Each conformer receives its own ordered predictions. The implementation performs neither conformer averaging nor Boltzmann weighting, and does not guarantee that generated conformers are distinct. Incomplete generation fails the requested collection rather than submitting the available subset. Generated coordinates and their stereo annotations are not independent experimental validation. Sources: ConformerShortfall, GENERATED_LIMITS and generated-result construction, and generation fixtures and qualification.

This local generator should not be described as the paper's exact coordinate production procedure: the paper reports RDKit embedding followed by MMFF optimization, while the local _embed path calls EmbedMultipleConfs and does not apply that optimization. Sources: paper v1, Appendix A, “3D conformation generation” and local generator.

Input interpretation and format coverage

The provider separates interpretation of the user's instruction from the deterministic readers and scientific model. For pasted input, the interpreter passes coordinate text, format (table or xyz) and source unit to prepare_pasted. Recorded text positions refer to that received text, not to byte offsets in the original Job. A successful preparation selects its geometry without another confirmation exchange. SMILES generation and verified Upload selection use their separate tools. Sources: interpreter conversation and tools, preparation and retirement orchestration, pasted source binding, tool definitions and terminal selection, and fixture rationale.

Pasted input accepts one geometry; multi-record XYZ/SDF input uses Upload selection with explicit order. Selected records are evaluated separately; molecular or stereochemical equivalence between records is not checked. Reader support includes coordinate tables, XYZ, V2000 MOL/SDF, PDB and MOL2, with format-specific constraints. Supporting a reader does not establish a complete real-interpreter/API run for that format. The fixture reference identifies authored cases and expected atom/record mappings; the preparation reference identifies format authorities, native-parser restrictions and exact runtime evidence.

The GUI packages attached files and folders as ZIP archives. For attached input, each analysis selects one structure file, which may contain multiple records. If an archive contains several files, identify the intended file by its exact name, including any folders, and state which records to use. For example: Use structures/butane.sdf, all records in file order, in angstroms. For XYZ or SDF, a selection such as records 2 then 1 uses the 1-based record numbers in that order. Repeated member names must be made unique before submission. Sources: GUI file selection and archive packaging; file and record selection instructions; exact member selection and refusal reasons.

For archived input, each result geometry records two source identities. Its source.sha256 and source.byte_length describe the molecular file actually read. The nested source.archive records the outer ZIP's hash and byte length, plus member_name identifying that file inside the archive. These hashes and lengths describe different bytes and need not match. Atom positions and record numbers refer to the molecular file, not the ZIP. Direct-file inputs retain their original file identity without an archive block. Sources: prepare_upload source binding; _planned_supplied result provenance. The qualification record, R47–R48, separates those tests from earlier native prediction evidence.

A locally qualified API Job supplied a ZIP containing two carbon-only SDF records. The real interpreter selected both records in three turns without corrections; the provider returned eight carbon shifts, each exactly matching the retained native fold-0 reference. The result preserves separate ZIP and SDF hashes, record order and supplied atom identities. This is a repeatability observation, not independent experimental accuracy. Sources: R53, successful API delivery: exact Job/Attempt/result and artifact hashes; preflight_sdf_zip and compare_sdf_scientific_documents, executed caller revision. Browser submission was not part of this run.

In separate checks, the real interpreter reported missing coordinate units, conformer count and record selection, and reported the mass-spectrum-only input as unsupported. Those model reports are not independently verified validation results. Three further cases selected MOL, PDB and MOL2 reader options, including the explicitly requested record order. These seven authored cases used inert attachment metadata: they exercised input decisions without file parsing, API Jobs or scientific inference. Their observations complement the separate native-reader and API evidence. Sources: R54, per-case outcomes: exact source/image and evidence hashes; run_batch and _FormatChoiceOnly, executed probe revision.

Published accuracy and the five-checkpoint ensemble

MAE is the mean absolute prediction error; RMSE is the square root of the mean squared error and gives more weight to large errors. Atom-level evaluation keeps the assigned atom correspondence. Sorted molecule-level evaluation compares within-molecule shift collections and cannot by itself establish that a predicted value belongs to the correct atom. Sources: pinned reg_metrics and sorted molecule evaluation.

The published NMRNet + Semi-supervised results below describe benchmark evaluation. They are not measured errors of this repository's local fold-0 reference or uncertainty bounds for an individual prediction. Source: Jin et al., arXiv:2601.18524v1, Table 2.

The released evaluation script runs folds 0–4, averages their prediction vectors, then computes errors. It does not average five error scores. Molecule-level evaluation additionally sorts predictions and targets within each molecule, so it measures a different correspondence from assigned atom-level error. The averaging attribution comes from pinned code and released logs; the paper's methods do not explicitly spell it out.
