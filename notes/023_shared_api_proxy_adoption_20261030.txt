NMRNet adoption of the host-owned API proxy
==========================================

Status: design, 30 October 2026. Implementation and deployment remain to be done.
Canonical shared design and proxy ownership belong to nmr-provider-tools note
020. NMRNet owns its consumer, local lifecycle
and retirement changes. This note records public contracts and relative source
references; instance settings and operational evidence stay private.

Outcome and completion
------------------------

NMRNet borrows one host-owned API socket. Its provider remains network-isolated,
signs its own requests and verifies API TLS through CONNECT. Delivery retains its
original binding, intake, durable queue and exact command/retry semantics. Native
prediction, reader and smiles workers, interpreter/store routes, lifetime locks,
models and scientific settings keep their existing ownership.

For this refactor, preserving old configuration while preparing its replacement
and avoiding interruption of old delivery are not requirements, including when
delivery has results to send. Configuration may be replaced and services may be
interrupted during cutover. Use existing storage ownership, signing/TLS and queue
semantics; add no staging, continuity or rollback system for the old topology.

All four providers AND delivery must use the shared proxy, with the eight old
API proxies retired, to complete the joint milestone. NMRNet's part requires its
actual running provider and maintained real-API paths to use the shared grant,
working API access and original delivery intake, and retirement of its old API
resources after their clients settle. A build or listener health alone does not
establish this. Correct retained retries need not finish before transport cutover;
a publisher paused by incorrect inputs must be repaired through its owner.

First integration is here against the existing API at nmr.localhost. Use real
providers and delivery through maintained workflows. Local results establish no
remote deployment claim. For each later authorized host rollout, push committed
source/issued artifacts, acquire them from GitHub there and build there. No side
checkout, transferred deployment bundle, copied image or private source overlay.

The first deployment establishes the proxy baseline: image selection, destination,
network settings, socket/group, storage and independent lifecycle. Later provider
improvements and SDK upgrades must not reconfigure, restart or replace that proxy
or recreate its socket volume. A deliberate later host-baseline change is separate
work under its owner. NMRNet's planned follow-ups require no new proxy capability.

Shared contract required before implementation
------------------------------------------------

Use the SDK's single client projection of a host-owned named volume, read-only
mount, socket path and supplementary access GID. Configuration belongs in existing
operator inputs and the shared binding admission path, without a second NMRNet
route definition. The concrete contract below is the current working agreement;
it is not an issued interface or release. Neither a release version nor instance
values are guessed here. The repository release record selects provider-core 0.5.2;
that is an inspected source pin, not a claim that it supplies this new interface.

The volume is external: true with its exact host-owned name. Clients cannot create,
initialize, relabel or remove it. Missing storage blocks launch and is reported to
the shared owner. There is no private fallback, cross-project depends_on or grant
of the router's network settings to the provider. Merge the API mount and GID with
existing mounts/groups, preserving the distinct delivery intake group even when
the two selected GIDs happen to match.

For one-off docker run clients, explicitly check that the exact borrowed volume
exists before launch: named-volume mounts can create missing storage, and nocopy
alone does not prevent that. Reuse the maintained launch owner for this check;
Compose's external declaration cannot protect a separate docker run invocation.

Working contract from canonical 020:

* One top-level api_proxy table in the existing binding TOML owns project, uid,
  gid, origin and route; per-binding API identities/trust/budgets remain. Selected
  client API origins must match the host's single allowed CONNECT authority.
* Socket storage derives from that project as <api_proxy.project>-socket. The
  public example project is nmr-api-proxy; instance selection remains private.
  Fixed client mount/socket are /run/nmr-api-proxy and
  /run/nmr-api-proxy/proxy.sock. This nested mount must coexist with NMRNet's
  existing /run tmpfs and separate delivery socket, without masking status files.
* provider_core.deployment_route.render_api_client(binding) returns exactly
  compose, client_socket, client_mount and client_group_add. compose declares
  only the shared-api volume alias, external with its exact derived name; the
  mount uses that alias, read-only and nocopy. client_group_add contains the
  decimal-string API GID. Merge these fields rather than replacing NMRNet grants.
* python -m provider_core.deployment_route client --definition FILE --binding NAME
  emits those same four JSON fields for one-off launchers. Resolve the alias via
  compose.volumes to the exact volume before inspection and docker run; never
  pass the Compose alias as a physical volume name. The Python consumer needs
  no image, runtime UID, namespace or resolver-relocation arguments.
* Selected-binding input_paths contains credentials and optional CA only. Host
  resolver access belongs to independent proxy rendering. NMRNet freezes its
  client projection and API inputs, without copying the host route settings.
* Selected DeploymentBinding.api_proxy contains project/gid only. The SDK's
  deployment_binding.client_definition_bytes(definition, *, binding_name) and
  client-definition --definition FILE --binding NAME action emit the selected
  binding and unchanged delivery settings as TOML, with api_proxy.project/gid.
  The capture CLI emits raw TOML, separately from the four-field JSON projection;
  do not run its output through a JSON decoder or extend ApiClientProjection.
  The same client loader accepts this capture without host uid/origin/route;
  host rendering requires those fields from the original operator definition.
  Consumers neither parse host policy themselves nor reconstruct stripped fields.
  Delivery needs the separate all-bindings export (binding_name=None in Python,
  --all instead of --binding in the CLI) to preserve all four original bindings.
  NMRNet continues using its selected-binding export; it does not assemble or
  install delivery's document. Delivery projects one shared API mount/GID for
  its bindings rather than four duplicate mounts at the fixed client path.

The shared-api alias does not collide with NMRNet's current physical-name volume
keys. The fixed socket requires no runtime CLI redesign: --api-proxy-socket already
accepts it.

The host proxy uses a nonroot UID different from consumer UIDs. Restricted group
traversal and socket connection must work from both Compose and one-off clients;
clients receive no lock/readiness ownership. The shared owner preserves the proxy
lifetime lock and stale-socket rules, with restrictive birth permissions:
directory 0710 and socket 0660. Resource budgets remain host-owned.

Before freezing the baseline, the shared owner must support this local API's
admitted destination and TLS hostname, ordinary combined traffic plus existing
maintenance reads, and current bounded CONNECT exchanges/reconnection. Capacity
is settled during initial joint bringup using existing traffic and bounded budgets;
no speculative 8x32 requirement, per-provider attribution or load campaign. Client
timeouts, signing identities, trust, operation certainty and retry classification
remain with their current owners. Proxy loss never proves that START failed or
authorizes replay, science rerun or rewritten queued commands.

Inspected source and concrete NMRNet changes
---------------------------------------------

1. nmrnet_provider/deployment.py::render_compose currently calls render_api_route
   with RouteDirectory(runtime / "route-api"), merges API services/networks and
   adds an API depends_on. Replace that entire production ownership with the SDK
   client projection. Add its external volume declaration, read-only mount, socket
   argument and supplementary group. Initialize networks from the scientific
   route needs rather than the removed API projection. Preserve provider network
   mode none, existing delivery/lifetime grants and the five local dependencies:
   prediction, reader, smiles, interpreter and store. Remove API-service-specific
   status handling and correct the obsolete fixed-service description.

2. tools/provider_deployment.py::freeze_deployment selects the original delivery
   binding and freezes API credentials/trust. Keep that selection and capture.
   Stop reading binding.route as network policy and copying api-resolv.conf.
   Freeze the admitted client grant in the existing Compose generation. Keep
   deployment.toml interpreter/store routes and their resolv.conf when needed;
   deleting API DNS capture does not remove scientific DNS authority.

3. tools/compose_deployment.sh::select_binding_inputs uses the SDK paths command.
   Adopt its new client-only file grants, preserving selected key/CA reads and
   removing API resolver grants. Stop creating runtime/route-api for new installs.
   SHARED_RUNTIME_IMAGE still selects code for owned scientific proxies and
   binding helpers; it does not select or redeploy the host API proxy. Keep
   immutable-image admission and existing source capture through committed inputs.
   Today this seam temporarily copies the full operator definition and grants it
   to the freezer; it does not retain that document in the published generation.
   Use the admitted snapshot with the SDK client-definition action, then give
   paths and the freezer that selected client TOML instead of the whole document.
   Keep binding_name unchanged so load_deployment_bindings(...).selected(name)
   still selects the original identity. Reparse the SDK-produced capture and
   compare the admitted client/delivery facts through the existing freeze path.
   Retain only the existing frozen config, credential/CA bytes and client grant;
   add no permanent definition copy or new configuration parser for NMRNet.

4. Lifecycle remains install/up/down/status/logs/retire-generations through
   tools/provider_deployment.sh. Existing install refuses a running project;
   up requires an empty project; down waits for successful provider exit before
   removing dependencies. Preserve these actual semantics for this cutover rather
   than promising seamless replacement. Repair any demonstrated settlement blocker
   at its owner without forced removal or a generic lifecycle rewrite.

5. Existing initialize_lifetime selects only the writable producer lock volume at
   /srv/nmrnet/attempts. Do not broaden that initializer to the API volume. Current
   retirement inspects all container mount sources, including stopped borrowers,
   and removes unused configuration bundles only. It does not remove runtime
   directories or named volumes. Preserve that boundary and add narrowly owned
   obsolete API-directory retirement to maintained tooling if needed for cutover,
   after all old clients/containers release it. Never scan/delete peer resources.
   Do not add a blanket exemption to journal, worker or lifetime ownership checks;
   only the specifically borrowed API grant is external wherever admission applies.

6. Convert maintained real-API staging paths in tools/provider_api_qualification.sh,
   tests/integration/provider_runtime/stage_api_config.py and binding_inputs.py.
   They currently author private API route settings for real-API provider runs.
   Use the same admitted shared client grant as production. Keep original caller
   identity, trust and retained Job readback; do not resubmit an uncertain Job.
   Trace direct real-API client networking in existing-pasted/api_prediction.py
   and use the shared CONNECT grant for that maintained API path as well. Preserve
   the separate interpreter ambiguity/model route: its destination is scientific,
   not the NMR API, despite using the same proxy implementation.

7. Disposable authored-API fixtures in compose_peer.py and offline Compose tests
   remain test infrastructure. Adapt their calls to the new SDK contract through
   the existing fixture owner; keep disposable route lifecycles confined there.
   They neither own the production host proxy nor require changing its destination
   to run tests. Do not remove a fixture's route merely because production stops
   rendering one. Audit remaining API route creation by caller and destination.

8. Adopt the issued SDK via the existing requirements/provider-core-release.json,
   install/native locks, package acquisition and image build paths. Update only
   affected dependency records through their owning tooling. Preserve scientific
   package/model identity; an SDK source/build check is not numerical proof.

Tier 1: first complete deployment and retirement
-------------------------------------------------

A. Converge this design and the SDK contract with Magnet, NMRPeak and SECS. The
   shared owner records the contract and supplies private host inputs and issued
   release. Continue unblocked source preparation; do not invent a release pin,
   copy SDK source or manufacture another provider identity while waiting.

B. Implement the owned seam and use the existing focused lanes:
   make test/integration/provider-core/compose and make test/unit/provider/deployment.
   Update normative/adversarial Compose/freezer checks and launcher fixtures to
   prove the API grant is external/read-only, both groups survive, scientific and
   delivery grants remain, and NMRNet creates no API service/network dependency.
   Retain current stopped-borrower and failure-before-deletion checks. Add only
   cheap cases needed for changed behavior or an observed failure; no new harness.

C. Build through maintained image targets. The controller and binding helper must
   both contain the issued SDK that admits client-only TOML. Bring up the shared
   proxy and check signed API access using an actual client with its intended
   identity, TLS trust, mount and supplementary groups. This may happen after
   stopping the old deployment; no incumbent-preserving preflight or separate
   check-api command is required for this refactor.

D. Use maintained down, install, up in that order for replacement. Retain lifetime
   storage, original delivery queue/intake, binding identity and exact commands.
   A blocked down is handled through its existing settlement owner; configuration
   preservation and uninterrupted delivery are not additional cutover gates.
   NMRNet never drives the independent shared services' lifecycle.
   Finish owned old API-directory retirement using the still-selected old recipe
   before install can prune it. Install automatically retires unused generations;
   once down removes the old containers there may be no borrower retaining that
   recipe. Do not defer ownership discovery until after installing the new plan.

E. Observe the running provider and all required workers/routes, selected images,
   shared socket/group, signed API read and original delivery intake. Check health,
   logs and restart counts through maintained paths. Account privately for pending
   or held delivery state; observe actual progress where work exists. A ready
   listener or preserved bytes cannot disguise a paused publisher. Reuse existing
   authorized local scenarios; no new synthetic science campaign is required.

F. Confirm NMRNet's old API container and unused private route directory were
   removed by the maintained down/retirement operations before install. Keep
   selected and stopped-borrowed generations. Shared owner retires old delivery API roles;
   each other provider retires its own. Verify ordinary NMRNet down/up and image
   maintenance leave the shared proxy and socket volume intact. Count actual API
   proxy roles across the joint topology, not just total containers.

G. Local completion requires all four providers plus delivery and old-proxy
   retirement. Record source, builds and observed running results separately.
   Later host rollouts repeat host-local acquisition/build/deployment checks,
   preserving confirmed milestones and each host's independent proxy baseline.

Recover components through their maintained workflows on the shared socket.
Do not restore an older durable queue, overlap queue owners, infer the outcome
of an interrupted request or recreate private fallback proxies. Keep existing
effect uncertainty; interruption does not change request or queue semantics.

Alternatives and reasons
--------------------------

Borrow a delivery-owned private proxy: rejected. Its lifetime and owner-only
permissions couple provider API calls to delivery replacement. A host-owned group
socket separates both services without sharing credentials.

Replace provider mount/group lists: rejected. It loses existing delivery intake,
lifetime and scientific grants. Add the small client grant at composition time.

Keep API network settings in every frozen generation: rejected. That duplicates
host authority and lets provider replacement appear to change the shared router.
Capture only client grant, API identity and trust; scientific routes stay local.

Make the provider host-networked or run it as root: rejected. Neither is needed
for a Unix socket grant, and both bypass current isolation. Fix actual group,
mount or trust faults without world-writable sockets or disabled TLS.

Introduce rolling-update orchestration, discovery or a route registry now:
rejected. The current finite lifecycle can execute the transport cutover; repair
demonstrated blockers narrowly. A second control plane adds maintenance without
helping the agreed first deployment.

Input replacement and owned retirement
----------------------------------------

Replace definitions through maintained configuration/provisioning; separate old
and new files and matching old-image recovery selections are not prerequisites.
The shared owner exports delivery's all-bindings client document and replaces its
publisher on the retained queue. NMRNet uses only its selected export. Original
binding identities, intake grants, signers and queued command bytes retain their
meaning even when delivery is interrupted with pending work.

Keep only the old recipe evidence needed to retire owned resources correctly.
NMRNet down loads its retained Compose recipe without reparsing DELIVERY_BINDINGS.
Use it to remove the old containers and identify the obsolete private API
directory; finish that scoped retirement before install prunes unused bundles.
This is a cleanup dependency, not a requirement to keep old configuration usable
or maintain an old runtime. Keep down/status and retirement usable from the
upgraded main checkout through retained Compose/Docker facts, without an old SDK
parsing the new definition. Do not add a compatibility reader or fake borrower.

Bring up the host proxy, check a real signed client, convert delivery and ready
providers through their maintained paths, and retire obsolete API resources.
Service interruption and configuration replacement are accepted during this
sequence; neither an empty queue nor uninterrupted publisher service is a gate.
Stop the old queue owner before starting its replacement, using the existing
delivery lifecycle. A concrete settlement or cleanup failure is repaired narrowly
at its owning command. Each provider keeps its own lifecycle; readiness of all
other providers is not a prerequisite for NMRNet's conversion.

Tier 2 and excluded projects
-------------------------------

NMRNet follow-ups remain in docs/notes/022_shared_delivery_deferred_20261024.txt,
under their existing owners and triggers. In this refactor, improve client
status/help, simplify client code exposed by integration and add regressions for
demonstrated faults after Tier 1. NMRNet owner revisits those when changing the
affected client/lifecycle path. These improvements must use the deployed proxy
contract and capacity, without a shared proxy operation. Recheck latest owning
status before treating an older deferral as open; do not duplicate historical
incidents or private cleanup inventories here.

Tier 3 excludes multiple APIs, dynamic registration, provider attribution or
fairness in the encrypted listener, a new configuration model, migration framework,
full-topology harness, exhaustive stress/chaos campaigns and independent science
qualification. None is a promised continuation. An observed correctness failure
belongs in Tier 1 even when broader work in that category is excluded.

Cross-provider findings
--------------------

Magnet notes/048_shared_api_proxy_adoption_20261030.txt distinguishes real-API
candidate validation from authored-API fixtures. NMRNet likewise converts its
maintained real-API clients while preserving independently owned fixture routes.
Its current proxy storage is a host bind directory and retirement is bundle-only;
Magnet's volume-checker assumptions do not apply to that directory.

NMRPeak notes/010_shared_api_proxy_adoption_20261030.txt identifies implicit volume
creation by one-off docker run clients, including mounts with nocopy. NMRNet's
one-off launchers therefore resolve the exact volume name and check existence.

SECS notes/010_shared_api_proxy_adoption_20261030.txt identifies the old-service
inventory trap. NMRNet retires its old project using the retained original recipe
before installing the new service set. Inspection against only the new plan
cannot establish ownership of removed roles. Scientific/model routes remain
independently owned in every provider.

NMRNet's freezer already selects by name through the SDK and needs API/delivery
facts rather than host routing fields. The selected client TOML fits that existing
boundary; the private rendering/resolver capture uses of binding.route disappear.
Keep fixture route inputs explicit at their test-owned boundary rather than
restoring production route fields to client captures. The four-field client grant
and raw-TOML capture remain separate interfaces. Compatibility must be checked
against the issued SDK during implementation; source review alone cannot prove it.
