NMRNet adoption of the shared API proxy and outbox
=================================================

Status: design, 30 October 2026. The authoritative joint design is
nmr-provider-tools/notes/020_shared_api_proxy_redesign_20261030.txt. No source
conversion, SDK release or deployment is claimed here.

Outcome and boundaries
----------------------

NMRNet uses two independently managed host services: an API CONNECT proxy for
its signed API exchanges and a durable outbox for terminal result handoff. Each
has one shared socket volume and access group. NMRNet borrows both read-only;
it cannot create, initialize, remove, restart or reconfigure either service.
The outbox uses the same API proxy for publication. Provider restart or removal
does not remove accepted work or the material needed for outbox retries.

The first joint deployment uses the existing nmr.localhost API: all four providers
and the outbox operate through the shared grants; eight old API proxies and unused
private API and delivery intake resources are retired. Actual API access, delivery
progress when work exists, pending work, health and retirement are observed. A
build, listener or single provider does not establish the joint outcome. Local
results do not establish remote deployment. Each host acquires source and issued
artifacts through GitHub and builds there using maintained targets.

Old configuration preservation and uninterrupted delivery are not cutover gates,
even with pending results. Configuration can be replaced and services interrupted.
Existing queue ownership, exact accepted commands, signing/TLS and uncertainty
rules still apply. Do not overlap queue owners, discard or retarget retained work,
or replay an uncertain START or rerun science to manufacture progress.

Shared contract needed by NMRNet
--------------------------------

The SDK supplies both client grants and a self-contained terminal handoff. Its
exact symbols, volume names, socket paths, groups and wire format remain to be
agreed with the shared owner; no previously proposed static binding projection,
per-provider socket or release version is assumed. A provider joins using the two
grants and its own API inputs, without delivery registration or an operator edit.

The handoff contains the exact terminal operation/body, Job/Attempt and API/provider
identity, API settings, original issued signing credential and optional CA material.
Pass usable credential/trust bytes through the SDK contract: provider-container
paths, in-memory key objects and pre-signed requests are not sufficient transport.
The outbox durably commits the result and publication inputs together before ACK,
and signs each retry itself. An ambiguous ACK leaves the original producer
obligation under existing reconciliation rules; durable acceptance is not API
acceptance. Protect retained secrets and queue/WAL/backup data; never put them in
logs, status, exceptions or public notes. Rotation or revocation cannot silently
substitute another identity; retained work must be held or failed visibly by its
owner if its authority cannot be used.
An acknowledgement on replay must reflect the inputs actually retained; changed
publication material cannot silently replace the original or be claimed stored.

Use additive API and outbox mounts/groups alongside the lifetime, native,
interpreter and store grants. Both shared volumes are external and excluded from
ordinary and custom deletion. A one-off docker run client must check the exact
volume exists before launch; nocopy alone can create a named volume. Preserve
provider network_mode none, client-side signing/TLS and independent scientific
routes. The shared intake is a trusted local submitter boundary. The SDK's
credential parser checks artifact fields and matching key pair; that alone does
not prove API issuance or authorization. The API authenticates publication.
There is no provider queue-read operation or secret disclosure in replies, but a
conflict refusal for a guessed matching identity can reveal limited existence
information; this limited disclosure is accepted for the controlled host. Apply
per-provider and total limits without a provider registry;
do not claim cryptographic per-provider socket authentication or zero metadata
leakage.

The provider-facing outbox supports only submission and its acknowledgement or
refusal; there is no pending, capacity, inventory or status read. Operator
inspection remains separate. NMRNet must replace both its pending-capacity gate
and queued-Job exclusion. A refusal after computation is not equivalent to the
former pre-start capacity check.

NMRNet's result.py currently bounds the public result at 786432 bytes. Keep
that result-body budget; bound the complete handoff for supported body plus
credential, CA and encoding overhead. The existing 2 MiB intake ceiling cannot
be assumed adequate for all providers' larger bodies and publication inputs.
Reject oversized inputs visibly at the owner; never truncate a result or its
publication material to fit the envelope.

One host-owned operator input controls live proxy capacity, logging and allowed
CONNECT authorities and outbox capacity, retry and logging. Provider replacement
must not restart the proxy or recreate its socket. Lower capacity affects new
admission without dropping active tunnels or pending work. Invalid reload retains
the last applied settings and reports failure; invalid startup fails visibly.
Host process identity, network and storage remain independently owned deployment
settings. Establish sufficient actual PID/thread/memory budgets for live limits.

Admission and bounded handoff without queue reads
-------------------------------------------------

Remove the pending() read in admission.py. Keep the authenticated API Job feed's
has_provider_execution_attempt=false filter and existing live claims. The API
implementation tests for any Attempt by this provider regardless of state;
while that record exists, its Job is excluded. Do not infer permanent exclusion
if an Attempt is removed or an API observation is incomplete.

In the inspected API source, ordinary Job cleanup purges Attempts only for a
DELETED Job; targeted cleanup first sets that state. The unattempted feed requires
an OPEN Job, so this purge does not make the same deleted Job selectable. A
source search found no other production Attempt-deletion call; integration tests
have their own deletion calls. This evidence is provider-relative: the filter
uses the authenticated provider principal, which must remain the original
identity. It does not establish behavior for uninspected database operations,
other deployments, outbox capacity or producer crashes.

NMRNet's work loop processes one controller serially and the existing executor
retains its exact selected outcome while retrying full or unavailable delivery.
Keep that owner and its existing bounded live Attempt/report claims. While the
handoff is unresolved, do not release that owner or admit further work through
this loop. A full outbox can therefore be discovered after science, unlike the
old pre-start capacity gate. This is an accepted throughput and resource tradeoff,
not proof that the former gate still exists. Do not introduce a local queue or
reservation protocol to recreate it.

On verified durable ACK, the outbox owns the exact accepted handoff and retry
material; the producer releases its terminal claim under the existing lifecycle.
The API's provider-relative Attempt filter prevents selecting that Job again
while its Attempt row exists, regardless of terminal or expired state. Use that
existing authority rather than mirroring the outbox's queued Job inventory.
Confirm the deployed API's Attempt retention and identity assumptions as part of
normal integration; do not assert the behavior after a record is removed.

On producer restart, use existing START/checkpoint recovery and effect-certainty
rules. The terminal-selected checkpoint carries a digest/length, not body bytes;
a crash before durable outbox ACK can leave the original obligation unresolved.
Hold/report it under existing recovery rather than inventing a result, rerunning
science or claiming accepted bytes survived. A new local durable result journal
or restart barrier would strengthen this existing pre-ACK uncertainty, so neither
is a prerequisite for this transport cutover. Existing queue limits still bound
outbox storage; active-owner limits bound live producer retention, not results
lost before acknowledgement or every possible failure timing.

Concrete NMRNet changes
-----------------------

1. nmrnet_provider/deployment.py currently renders a private API RouteDirectory
   and derives a delivery volume from API/provider identity. Replace both with
   the SDK's shared grants. Add external read-only mounts and supplementary GIDs
   without replacing other grants. Remove private API services, dependency and
   resolver projection; keep the five native/interpreter/store dependencies,
   provider network isolation and the independently owned scientific routes.
2. tools/provider_deployment.py currently selects a static delivery binding,
   freezes its API credential/CA and copies its API resolver. Replace selection
   with existing provider-owned API configuration plus the two SDK grants. Keep
   client identity, trust and secret capture, but no outbox registration or
   per-binding router configuration. Retain interpreter/store DNS inputs when
   their independently owned routes require them.
3. tools/compose_deployment.sh currently obtains binding file paths and builds
   private route-api directories. Adapt its maintained install inputs to the new
   SDK contract and stop creating that API route. Preserve image admission and
   generation/worker lifetime ownership. The old route is a host bind directory:
   down and retire it using its old owning recipe before install's automatic
   generation cleanup discards the evidence. This is resource retirement, not an
   old-configuration continuity requirement.
4. nmrnet_provider/config.py currently constructs DeliveryEndpoint from identity
   and a per-provider socket; runtime.py and service.py use DeliveryClient. Adapt
   their existing configuration and terminal-handoff boundary to the new SDK.
   Ensure every terminal path carries admitted API settings and credential/trust
   material to the outbox, with no extra provider-side publication registry.
   Preserve existing durable acceptance, retry, shutdown and effect-certainty
   behavior. Replace pending-dependent admission using the API filter and bounded
   live owner above. Do not broaden signing material to scientific workers.
5. Convert maintained real-API staging/readback in tools/provider_api_qualification.sh
   and tests/integration/provider_runtime, including independently networked client
   paths, to the shared API grant. Preserve original readback identity and do not
   resubmit uncertain Jobs. Interpreter/model and store routes remain separate.
   Disposable authored-API fixtures retain test-owned routes and their cleanup;
   adapt fixture inputs without adding a production private-proxy fallback.
6. Adopt the issued SDK through existing requirements records, lock, acquisition
   and image build workflows. Do not guess a release, copy SDK source, alter model
   identity or treat a build as scientific or live-deployment proof.

Tier 1 rollout and checks
-------------------------

Implement the provider seam and use the affected existing Compose and provider
lifecycle checks. Check both external mounts/groups, retained native and scientific
grants, no private production API service, and self-contained handoff behavior
through the SDK's maintained tests. Cover a lost acknowledgement and retained
publication material through the existing owners; do not add a new topology or
stress framework. Actual SDK wire/secret handling needs source review once issued.

Bring up the host proxy and outbox, use an existing signed API check, then replace
ready providers through maintained down/install/up paths. Retirement of NMRNet's
old bind directory must precede install pruning its ownership recipe. Delivery
may be interrupted and old config overwritten; an empty queue is not required.
The shared owner converts actual old queued items with their original identity
and signing inputs. Missing inputs leave affected work retained and reported,
not discarded or retargeted. Resolve observed integration failures at their owner.

Observe NMRNet's actual image, shared socket/group grants, signed API access,
worker/scientific routes and outbox intake. Account for pending/held work and
observe publication progress when available. Confirm normal provider lifecycle
leaves both host services and their storage alone. The shared owner verifies all
four providers, the outbox and retirement of old private API/intake resources.

Later work and alternatives
---------------------------

Client help/status and small regressions for observed faults follow the first
joint deployment. Existing NMRNet follow-ups remain in
docs/notes/022_shared_delivery_deferred_20261024.txt.
Later provider changes use the running proxy and its live operator controls.
Multiple-API orchestration, dynamic registration, per-provider proxies and new
migration/load frameworks are outside this work unless a concrete need arises.

Sharing an old delivery-owned proxy would couple direct API calls to outbox
lifetime. Running proxy and outbox in one process has the same failure-domain
problem. Static delivery bindings and dedicated intake sockets require operator
edits when providers join or leave and leave publication authority outside the
accepted item. The two independent shared services and self-contained handoff
address those problems while keeping scientific routes and client TLS independent.
