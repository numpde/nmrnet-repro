Third slice: a contained NMRNet++ provider for the NMR API
Date: 2026-10-18
Author: repository coordinator
Status: implementation plan; implementation has not started

Purpose and completion
======================

Turn the qualified coordinate predictor into an NMR API offering: a commissioner
submits one explicit molecular geometry, the provider predicts its H/C shifts,
and an authorized receiver reads the result through the API. Developers and
operators must also receive useful safe reasons when that path cannot finish.
003 is complete when that entire workflow and its failure/recovery cases pass
against the actual API in a contained local deployment, with portable evidence
and maintained operating instructions. Production activation is a separate act.
Readiness, a mock API, or the existing scientific tests alone cannot close 003.

Starting point: nmrnet-repro revision
7e320505fdbee228e312778032b144cc14ef38b9, including closed notes/001 and 002,
the pinned NMRNetplusplus submodule, nmrnet_inference/{predict,model,release}.py,
artifacts/prediction-models.json and artifacts/prediction-cpu-float32.json.
002's packet SHA-256 is
3054ace5fb17b824e114c65c25e24389eca7551e38a0aece7f347f5b98f5fa75.
Its evidence covers CPU float32, the selected fold-0 pair, four retained fixtures,
64 exact historical positions, 137 outputs and real 128-atom capacity. It does
not establish general chemical accuracy, five-fold ensemble accuracy, inferred
bonds, or the original archive producer's coordinate units.

Initial offering decision
=========================

Plan one coordinate-input offering. The complete Job specification text is one
JSON object with exactly coordinate_unit, atoms, coordinates: the existing 002
request. Encode the verified text as exact UTF-8 and pass those same bytes to
the callable. JSON whitespace is allowed; prose, Markdown fences, URLs, uploaded
files, molecule names, SMILES and multiple molecules are unsupported. Explain
this in the offering description and input errors. Do not add an LLM interpreter
to extract numerical geometry. Rationale: [I1], [M2], [P1] permit a deterministic
bridge to the already qualified boundary without an unqualified chemistry step.

The API's 65,536 UTF-8 byte limit is the effective offering ceiling, within the
callable's existing 1 MiB bound. Preserve its 1-128 atom bound, exact angstrom
label, finite float32 coordinates, dictionary admission and duplicate/extra-field
rejection. No reserialization, atom repair, unit conversion, implicit hydrogens,
geometry optimization or caller-selectable checkpoint/device/precision/solvent.
Require angstrom even for context-only empty-output requests at the provider
boundary: 002's parser checks unit agreement only for present H/C heads. This is
an explicit offering restriction, tested without changing the scientific callable.
The caller supplies the full desired atom inventory, including hydrogen atoms.
Predict every supplied H/C atom once at its original zero-based index. Skip
absent heads; an input with neither H nor C retains the callable's successful
empty result, described explicitly. Do not copy G01's absent-nucleus rejection.

An input example in the offering must be a complete molecule with documented
geometry provenance and a distribution basis; do not label the two-atom shape
example in 002 a chemically qualified molecule. Scale remains the adopted
angstrom convention, supported by the NIST tests, not archive-wide provenance.
No bond graph, stereochemical validation, ensemble, uncertainty estimate or
spectral simulation is promised. SMILES/conformer generation is a later slice
with its own scientific and atom-correspondence qualification, if wanted.

Planned owners and grants
=========================

Use one pinned provider-core dependency [M1] and a repo-owned NMRNet binding.
Slice 1 must prove the core can be built and imported from its declared package
without ambient sibling checkout files. If its current packaging/API contract
cannot support this, record the precise missing seam and revise this decision
before lifecycle implementation; do not silently vendor its entire application.
No installed software is acquired in this planning task. Future acquisition uses
the existing explicit-interface, advisory review, lock and offline-build workflow.

Provider container: owns verified API Job/Attempt interactions, signing material,
the input binding, result/failure projection and bounded durable Attempt state.
Inference container: owns only bounded private request exchange and the existing
predict_request + SelectedReleaseModels composition. Keep H then C sequential,
release each head, and permit one active inference per runner. Reject concurrent
admission instead of silently creating an unbounded queue or model copies.
Use the existing runner-session mechanics [M2] when compatible; declare and test
the NMRNet-specific input/result framing once. A public prediction CLI is not a
deliverable. Do not change NMRNetplusplus without prior discussion.

All Python, tests, package operations, API fixtures and scientific execution run
in contained containers. Host shell/Make/Git only orchestrate. Reuse current
image/source admission and container guards; lock any new runtime closure and
qualify the actual final images without incidental workspace imports. Pin API
and core revisions and any client dependency used by the test deployment.

Inference retains network=none, read-only root/model/source mounts, nonroot UID,
cap-drop ALL, no-new-privileges, 2 CPUs, 4 GiB/no swap, 64 PIDs and bounded scratch.
Only a dedicated private socket directory crosses provider/runner containers;
no model-container credentials, engine socket, home or entire-workspace mounts.
Provider gets only its necessary credentials/configuration/state and explicit
API network access, with its own measured CPU/memory/PID/scratch and storage bounds.
External network egress (API access or acquisition) requires an explicit host
interface and proof of binding to it, with no ambient/default-interface fallback.
For the provider, make that bound route its sole external API route and test
that direct connections cannot bypass it. Slice 1 chooses the enforcing network
mechanism; proxy configuration alone does not enforce this. The current acquisition
lane's host-network client and bound proxy (tools/docker.sh, tools/bound_http_proxy.py)
are not evidence of provider bypass denial; this is a new provider requirement.
Inference itself needs none because it is offline. Local API/GUI qualification
uses an explicitly named internal container network and disposable credentials;
test denial of external egress, not merely membership of a NAT-capable bridge.
This internal network is a distinct grant, not a substitute for host-interface
selection when reaching an external API. No production endpoints are used.

Host orchestration owns container startup/teardown. For the initial runner,
cancellation or uncertain in-flight execution requires retirement of that exact
runner container. The host owner must confirm engine-reported termination before
replacement readiness or another inference admission; engine-confirmation failure
leaves execution unresolved and admission blocked. Neither service gets an engine
socket. Successful requests and determinate input rejections may reuse the runner.
Slice 1 must name and prove the actual bounded control path from cancellation to
the host's retirement owner; an unspecified supervisor is not a design. Lost
connection or a killed local helper alone is not proof that work ended. This
lifecycle extension needs new evidence; 002's one-shot TERM proof is a starting
point. Record startup/request/retirement deadlines as explicit tested deployment
settings; do not invent values from unrelated model timings.

Result and failure contract
===========================

Keep the scientific result: unit=ppm, predictions containing atom_index, element,
shift_ppm in supplied order. Validate complete eligible coverage, finiteness and
index/element agreement before API completion. Neither a partial H success nor a
malformed runner response can become a successful result. In slice 1 choose the
actual offering/implementation/result schema identifiers permitted by [M1/I2]
and bind them consistently in registration, description, runtime and tests.
Placeholder identifiers or a mismatched runner contract must prevent readiness.

The result observation must link original Job/input identity, the scientific
input byte identity, atom-index convention and fixed model/runtime provenance.
Keep that metadata at one result owner, not repeated per atom. Publish only
facts useful to authorized recipients; no host paths, secrets or raw input copies
in generic diagnostics. The precise envelope and result byte ceiling are frozen
in slice 1 against the API consumer. Canonicalize the output through the existing
publication owner [I2/M1], not the scientific input bytes. Replaying an already
prepared terminal result reuses exact bytes and identity, not fresh inference.

Errors, but not secrets, must propagate and maximally inform each recipient.
Preserve cause, phase, effect state and useful recovery action. Classify failures
at their owning phase: input admission, artifacts/configuration, runner exchange,
scientific computation, result validation, and API publication. Do not classify
all ValueError exceptions as invalid input or publish arbitrary exception text.
The existing callable preserves exceptions; its provider boundary must translate
only known safe facts and retain bounded causal evidence [S1, 013 U23/A03].

Recipient acceptance:
- Developer: phase, cause chain, relevant source location and safe diagnostic
  facts in protected, bounded provider diagnostic records, read through the
  documented contained operator inspection command; no local-variable dumps.
- Operator/deployer: Attempt/service identity, whether work stopped or reporting
  is pending, actionable configuration/resource/network reason and recovery step,
  using those diagnostic records and the core's stopped-journal inspection [M4].
- Commissioner: rejection vs operational failure vs still-unresolved status,
  safe specific explanation and what to change or wait for through the API and
  the pinned GUI Attempt view [G1]. Use only supported API condition codes.
- Receiver: a readable result with units/atom correspondence/limits, or an honest
  indication that no result exists, using [G1]'s JSON/text view and byte download.
  Verify the original indices, units, provenance and limitations are visible for
  the maximum result within its preview bounds. No new GUI renderer is promised.

Test nested causes, traceback/notes, parser errors, unknown exceptions, oversized
reasons, socket loss, output capture and secondary cleanup/reporting/storage
failures with private sentinels. Check both safe diagnostic detail and absence of
secrets/scientific payload in each unauthorized channel. Preserve primary and
secondary failures; a failed report must not rewrite successful inference or
claim API publication. Use bounded diagnostics and visible truncation [S1].

API start/completion/failure ambiguity belongs to the lifecycle owner [M1/I2].
Recover/reconcile the same Attempt and immutable prepared outcome before accepting
another obligation; never infer a terminal state from a transport timeout. Test
restart before/after request transmission and before/after terminal commit with a
lost response. A retry disposition needs explicit safety evidence. Persist only
state needed for recovery and authorized diagnosis with restrictive access and a
bounded retention policy. Storage failure must block unsafe progression and be
visible to operators. Confirm remote state before retiring the owned journal.

Server expiry [I3] can occur during inference, outage or lost-response recovery;
progress does not extend it. On confirmed expiry stop owned computation and
confirm retirement, retain safe evidence of any unreported result, and do not
resend completion/failure or fabricate a new Attempt. Retire the active obligation
only after authoritative terminal reconciliation, worker quiescence and required
evidence retention; then unrelated Jobs may proceed under the existing lifecycle.
The pinned GUI shows Expired, not a per-expiry recovery instruction. Put the
guidance in the offering description loaded by hello_description_path [M3] and
the operating guide at its full copyable URL [G1]: this Attempt has no published result; ask the
provider operator to resolve outstanding work before deliberately creating a new
Job. Do not promise renewal or automatic resubmission of the expired Attempt.
Verify the delivered offering help and actual GUI status, and do not hide results
from other Attempts on the same Job. If completion actually committed before
response loss, recover that exact success instead.
Slice 1 records the test API's maintenance policy and operational deadline budget;
no provider deadline can guarantee completion before server expiry. Test expiry
during inference and during lost-response reconciliation, including terminal
conflicts and service restart, without automatically rerunning the science.
